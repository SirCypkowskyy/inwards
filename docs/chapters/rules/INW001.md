# INW001 `layer-dependency`

## What it does

Reports an import, in a file that belongs to a layer, of first-party code that belongs to an outer layer. Layers are listed innermost first in `[tool.inwards]`, and a module may import its own layer and anything listed before it.

Every import in the file counts: top level, inside a function or class, and behind `if TYPE_CHECKING:` ([ADR-009](../05-ADR.md#adr-009-check-imports-wherever-they-appear)). Relative imports are resolved against the file's package, and `from shop import infrastructure` is resolved to `shop.infrastructure`. Dynamic imports (`importlib.import_module("shop.infrastructure.db")`) are [INW011](INW011.md)'s job.

## Why is this bad

An outward import ties the inner layer to the details it is meant to be independent of: the domain can no longer be tested, read or reused without the database code. Agents make this edit often, because importing the class that already does the job is the shortest path to working code. Review catches it late, if at all. The first thing an agent tries when the import is flagged is to hide it, in a function or behind `TYPE_CHECKING`, so the rule checks those places too and the fix says so.

## Example

The layers of this example, which the other rule pages use too:

<!-- e2e -->

```toml title="pyproject.toml"
[tool.inwards]
layers = [
  { name = "domain",         modules = ["shop.domain"] },
  { name = "application",    modules = ["shop.application"] },
  { name = "infrastructure", modules = ["shop.infrastructure"] },
]
```

The domain reaches into the infrastructure for a class that talks to the database:

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.infrastructure.db import SqlOrders


def total(order_id: int) -> int:
    return SqlOrders().total(order_id)
```

<!-- e2e -->

```sh
inwards check
```

<!-- e2e -->

```text
shop/domain/order.py:1:36: INW001 Layer "domain" imports "shop.infrastructure.db.SqlOrders" from outer layer "infrastructure". Allowed direction: domain <- application <- infrastructure.
  fix: Depend on an abstraction owned by "domain" instead of "shop.infrastructure.db.SqlOrders".
    1. Delete `from shop.infrastructure.db import SqlOrders`. Do not move the import into a function or behind TYPE_CHECKING; Inwards checks those too.
    2. Declare a typing.Protocol in `shop.domain` (for example `shop.domain.ports`) that describes only what this module needs from `SqlOrders`.
    3. Type this module against that Protocol and receive the implementation through a constructor or function parameter.
    4. Make the class in "infrastructure" satisfy the Protocol, and wire it in the outermost layer (the composition root).
  docs: https://sircypkowskyy.github.io/inwards/rules/INW001/
```

Fixed: the domain owns a port, and the infrastructure implements it.

<!-- e2e -->

```python title="shop/domain/ports.py"
from typing import Protocol


class Orders(Protocol):
    def total(self, order_id: int) -> int: ...
```

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.domain.ports import Orders


def total(orders: Orders, order_id: int) -> int:
    return orders.total(order_id)
```

<!-- e2e -->

```python title="shop/infrastructure/db.py"
class SqlOrders:
    def total(self, order_id: int) -> int:
        return 0
```

<!-- e2e -->

```sh
inwards check
```

`SqlOrders` satisfies `Orders` structurally, so it needs no import of the domain. The composition root, in the outermost layer, passes a `SqlOrders()` to `total`.

## How to fix

1. Delete the import. Moving it into a function, behind `TYPE_CHECKING` or into `importlib` only moves the finding.
2. Declare a `typing.Protocol` in the inner layer that describes only what the module needs.
3. Type the module against the Protocol and take the implementation as a constructor or function parameter.
4. Let the outer class satisfy the Protocol, and wire the two together in the outermost layer.

If the module really belongs in the inner layer, move it there instead. If the layers themselves are wrong, that is the user's call: the fix never tells an agent to edit `[tool.inwards]`, and the config guard stops it.

## Fix safety

Inwards has no automatic fix for this rule (`autofix: false`). The steps above change the design, so they need a person or an agent to carry them out and a review of the result.

## Configuration

Severity error. `[tool.inwards.rules]` can turn the rule off (`ignore = ["INW001"]`) or make it a warning (`severity = { INW001 = "warning" }`); see [Configure rules](index.md#configure-rules). To accept one import, suppress it on its line:

```python
from shop.infrastructure.legacy import LegacyClient  # inwards: ignore[INW001] reason="old billing adapter, removed in #210"
```

For a parenthesised import, the comment goes on the imported name's line. The Claude Code hooks don't honour a suppression the agent added during the session unless `agent-suppressions = "allow"` ([ADR-028](../05-ADR.md#adr-028-inline-suppressions-need-a-reason-and-an-agent-cant-add-one-by-default)).

In the Claude Code hooks, a violation blocks the edit that adds it and the Stop gate. A violation the file already had when the session started goes to the agent as context instead, so legacy code doesn't block an unrelated edit.

## Known limitations

- Layer membership is by module prefix only. Globs such as `shop.*.domain` for vertical slices come with the config schema v2 ([#51](https://github.com/SirCypkowskyy/inwards/issues/51)).
- There is no opt-out for type-only references to an outer layer ([ADR-009](../05-ADR.md#adr-009-check-imports-wherever-they-appear)).
- Imports inside first-party code that belongs to no layer aren't checked; [INW006](INW006.md) reports that code.
- In an implicit namespace package (no `__init__.py`), relative imports resolve as if the directory were a regular package.
- A symlinked directory inside a layer that points outside the project isn't checked ([#83](https://github.com/SirCypkowskyy/inwards/issues/83)), and a symlinked alias inside one layer that points into another can hide an outward import ([#84](https://github.com/SirCypkowskyy/inwards/issues/84)).
