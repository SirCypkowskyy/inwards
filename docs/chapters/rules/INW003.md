# INW003 `public-api-only`

## What it does

Reports an import, from outside a [context](../guides/configuration.md#contexts), of one of the context's modules that isn't public. A module is public when it lies at or under one of the context's `public` prefixes: `public = ["shop.billing.api"]` opens `shop.billing.api` and everything under it, and nothing else in `shop.billing`.

- The caller can be in another context or in no context at all, such as an entry point or a script. Only code inside the context itself may import its internals.
- An import from a context that doesn't declare the target in `depends-on` is [INW002](INW002.md)'s, and gets no INW003 as well: the dependency itself has to go, whichever module it goes through.
- An imported name counts as the module it lives in: `from shop.billing.invoices import issue_invoice` imports `shop.billing.invoices`.
- The fix names the public module that already exposes the imported name, by defining it or importing it, when one does.

Every import counts, as for INW002: relative ones, imports inside functions or behind `TYPE_CHECKING`, and dynamic imports whose target Inwards can read. The rule applies whether or not a layer owns the file.

## Why is this bad

A context's public modules are the promise it makes to the rest of the code; everything else can change without notice. A caller that imports an internal module ties itself to how the context is built today, so a rename or a split inside `billing` breaks `orders`. An agent looks for the name it needs and imports it from wherever it is defined, which is usually an internal module. INW003 points it at the public one.

## Example

Orders may use billing, and billing's public module is `shop.billing.api`, which re-exports the invoice function:

```sh

```

```toml title="pyproject.toml"
[tool.inwards]

  { name = "slices", modules = ["shop.orders", "shop.billing"] },
]

[[tool.inwards.contexts]]
name = "orders"
modules = ["shop.orders"]
depends-on = ["billing"]

[[tool.inwards.contexts]]
name = "billing"
modules = ["shop.billing"]
public = ["shop.billing.api"]
```

<!-- e2e -->

```python title="shop/billing/invoices.py"
def issue_invoice(order_id: int) -> None:
    pass
```

<!-- e2e -->

```python title="shop/billing/api.py"
from shop.billing.invoices import issue_invoice

__all__ = ["issue_invoice"]
```

<!-- e2e -->

```python title="shop/orders/checkout.py"
from shop.billing.invoices import issue_invoice
```

<!-- e2e -->

```sh
inwards check
```

```text
shop/orders/checkout.py:1:35: INW003 Context "orders" imports "shop.billing.invoices.issue_invoice" from context "billing", but "shop.billing.invoices" isn't one of its public modules.
```

```python title="shop/orders/checkout.py"
from shop.billing.api import issue_invoice
```

## How to fix

1. If the fix names a public module, import the name from there instead.
2. Otherwise, re-export what you need from one of the context's public modules (`from shop.billing.invoices import issue_invoice` in `shop/billing/api.py`), then import it from there. That is a code change, not a config change.
3. If the context declares no public modules, ask the user which of its modules other code may import. The hooks don't let an agent edit `[tool.inwards]`.

## Fix safety

No automatic fix (`autofix: false`). A public module that exposes the same name usually exposes the same object, but it doesn't have to, and re-exporting a name from a public module widens the context's promise. Both are decisions to check.

## Configuration

Severity error. The rule reads `public` in `[[tool.inwards.contexts]]` and does nothing without contexts; the [configuration reference](../guides/configuration.md#contexts) has every key. A context without `public` keeps all of its modules private. `[tool.inwards.rules]` can turn the rule off or make it a warning ([Configure rules](index.md#configure-rules)).

One import can be suppressed on its line, with a reason:

```python
from shop.billing.invoices import issue_invoice  # inwards: ignore[INW003] reason="api.py lands in #91"
```

## Known limitations

- `public` entries are prefixes, so a package's `__init__` can't be public without everything under it ([ADR-030](../05-ADR.md#adr-030-bounded-contexts-as-a-contexts-table-of-literal-prefixes)). Put the public names in a module of their own, such as `api.py`.
- To name a public module, the fix looks for a top-level `def`, `class` or assignment of the name, or an import of it. A re-export under another name (`import x as y`) or through `__all__` alone isn't found; the import is still reported, with the general advice.
- A dynamic import whose target Inwards can't read isn't reported here. In a layer, [INW011](INW011.md) reports it.
