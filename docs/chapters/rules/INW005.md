# INW005 `pure-domain`

## What it does

Reports an import, in a file in a layer, of a library the layer may not use. Each import is sorted into first-party (a layer or the project owns it, left to [INW001](INW001.md) and [INW006](INW006.md)), standard library (a bundled list of CPython 3.11 to 3.14 module names) or third-party. A library import is then checked against three optional layer keys:

- `allow-libraries`: once set, the layer may import only these third-party libraries. The standard library stays allowed.
- `deny-libraries`: the layer may not import these, standard library included. On the innermost layer it replaces the default deny list.
- `extend-deny-libraries`: adds to the layer's deny list, the default one included.

Without any of them, the innermost layer of a config with two or more layers denies a default list: frameworks (`django`, `fastapi`, `flask`...), databases and ORMs (`sqlalchemy`, `psycopg`, `redis`, `sqlite3`...), network clients (`requests`, `httpx`, `boto3`...) and stdlib I/O (`socket`, `subprocess`, `http.client`, `urllib.request`...). Other layers may import any library. The import is checked wherever it is, as for INW001, including literal dynamic imports (`importlib.import_module("requests")`). [Libraries per layer](../guides/libraries.md) has the full list and the matching rules.

## Why is this bad

INW001 only looks at your own code, so `from sqlalchemy.orm import Session` in the domain passes it, even though it ties the domain to a database as firmly as `import shop.infrastructure.db` would. For an agent told not to import the infrastructure layer, importing the library directly is the obvious next move. It is also the most common leak in layered Python code written by people.

## Example

With the layers from [INW001](INW001.md#example), the domain uses an ORM session:

<!-- e2e -->

```python title="shop/domain/order.py"
from sqlalchemy.orm import Session


class Order:
    def __init__(self, session: Session, order_id: int) -> None:
        self.session = session
        self.order_id = order_id
```

```sh
inwards check
```

<!-- e2e -->

```text
shop/domain/order.py:1:28: INW005 Layer "domain" imports "sqlalchemy.orm.Session" from library "sqlalchemy", which "domain" may not use.
  fix: Use "sqlalchemy" in an outer layer, behind a port owned by "domain".
    1. Delete `from sqlalchemy.orm import Session`. Do not move the import into a function, behind TYPE_CHECKING or into importlib; Inwards checks those too.
    2. Declare a typing.Protocol in `shop.domain` (for example `shop.domain.ports`) that describes only what this module needs from "sqlalchemy".
    3. Type this module against that Protocol and receive the implementation through a constructor or function parameter.
    4. Implement the Protocol with "sqlalchemy" in the outer layer that holds adapters (allowed: "application", "infrastructure"), and wire it in the outermost layer (the composition root).
    5. If "domain" should be allowed to use "sqlalchemy", ask the user to add "sqlalchemy" to that layer's allow-libraries in [tool.inwards]. Don't edit [tool.inwards] yourself.
  docs: https://sircypkowskyy.github.io/inwards/rules/INW005/
```

Fixed: the domain declares what it needs, and the infrastructure implements it with SQLAlchemy.

```python title="shop/domain/ports.py"
from typing import Protocol


class Orders(Protocol):
    def total(self, order_id: int) -> int: ...
```

```python title="shop/domain/order.py"
from shop.domain.ports import Orders


def total(orders: Orders, order_id: int) -> int:
    return orders.total(order_id)
```

```python title="shop/infrastructure/db.py"
from sqlalchemy.orm import Session


class SqlOrders:
    def __init__(self, session: Session) -> None:
        self.session = session

    def total(self, order_id: int) -> int:
        return 0
```

## How to fix

1. Delete the import. Moving it into a function, behind `TYPE_CHECKING` or into `importlib` only moves the finding.
2. Declare a `typing.Protocol` in the layer that describes only what the module needs from the library.
3. Type the module against the Protocol and take the implementation as a parameter.
4. Implement the Protocol with the library in an outer layer that may use it. The fix lists every such layer; pick the one that holds adapters, which in a hexagonal layout isn't always the next one out.
5. If the layer should be allowed to use the library, that is the user's decision: they add it to `allow-libraries`. When no outer layer may use it either, the fix asks the agent to ask the user where the library belongs.

## Fix safety

No automatic fix (`autofix: false`). Moving a library behind a port changes the design and needs review.

## Configuration

Severity error. Per layer, in `[tool.inwards]`:

```toml title="pyproject.toml"
[tool.inwards]
layers = [
  { name = "domain",         modules = ["shop.domain"], allow-libraries = ["attrs"], extend-deny-libraries = ["os"] },
  { name = "application",    modules = ["shop.application"], deny-libraries = ["sqlalchemy", "requests"] },
  { name = "infrastructure", modules = ["shop.infrastructure"] },
]
```

Entries are import names (`yaml`, not `PyYAML`) that cover their submodules. When the allow and deny lists both match, the longer entry wins, and `allow` wins a tie. `deny-libraries = []` on the innermost layer turns the default off. `[tool.inwards.rules]` can turn the rule off or make it a warning (`severity = { INW005 = "warning" }`), see [Configure rules](index.md#configure-rules). One import can be suppressed on its line with `# inwards: ignore[INW005] reason="..."`.

## Known limitations

- Distribution names that differ from the import name aren't mapped: list `yaml`, not `PyYAML`.
- The standard-library list is fixed at build time, so a module added in a later CPython counts as third-party until Inwards updates the list.
- Adding the rule to an existing config with two or more layers can report libraries the domain uses on purpose. `deny-libraries = []`, an `allow-libraries` entry or `inwards baseline` accepts them.
