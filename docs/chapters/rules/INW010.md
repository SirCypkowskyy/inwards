# INW010 `unknown-first-party`

## What it does

Reports a static import, in a file in a layer, of a first-party module that doesn't exist, and a relative import that climbs above the top-level package, which Python always refuses. An import is first-party when a prefix of it is a module of the project.

Only the module part is checked: `X` of `from X import name`, and the whole name of `import X` or `from X import *`. Existence is probed on disk the way Python imports, so namespace packages, stubs (`.pyi`) and compiled extensions (`.so`, `.pyd`, `.pyx`, `.pyc`) count. The fix lists the three modules of the same package closest to the missing name. Packages whose `__init__.py` extends `__path__` (`pkgutil.extend_path`, `declare_namespace`) are skipped. A module that a [`generated`](#generated-modules) pattern covers counts as existing, since a build step writes it.

An import INW010 reports gets no [INW006](INW006.md) as well, and an outward import [INW001](INW001.md) reports gets no INW010: INW001's fix deletes the import, while INW010's would create the module.

## Why is this bad

Agents invent plausible modules: `from shop.domain.pricing import DiscountPolicy`, where `pricing` doesn't exist. Without a check it surfaces as an `ImportError` at test time, if a test covers the file. INW010 flags it in the same hook run, before any test is written, and points at the near miss the agent probably meant.

## Example

With the layers from [INW001](INW001.md#example), and `prices.py` and `money.py` in the domain:

<!-- e2e -->

```sh
touch shop/domain/prices.py shop/domain/money.py
```

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.domain.pricing import DiscountPolicy
```

<!-- e2e -->

```sh
inwards check
```

<!-- e2e -->

```text
shop/domain/order.py:1:33: INW010 "shop.domain.pricing" is not a module of this project: "shop.domain" has no "pricing".
  fix: Import a module that exists, or create "shop.domain.pricing" first.
    1. Check the name. The closest modules in "shop.domain": `shop.domain.prices`, `shop.domain.money`.
    2. If the code isn't written yet, create "shop.domain.pricing" before importing it.
    3. Don't wrap the import in try/except ImportError; Inwards checks those too.
  docs: https://sircypkowskyy.github.io/inwards/rules/INW010/
```

Fixed: the policy lives in `prices.py`.

<!-- e2e -->

```python title="shop/domain/prices.py"
class DiscountPolicy:
    pass
```

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.domain.prices import DiscountPolicy
```

<!-- e2e -->

```sh
inwards check
```

## How to fix

1. Check the name against the closest modules the fix lists, and import the one that exists.
2. If the code isn't written yet, create the module first, then import it.
3. Don't wrap the import in `try/except ImportError`: the rule checks it there too, and the code would still fail at runtime.

## Fix safety

No automatic fix (`autofix: false`). The closest name by edit distance isn't always the module the code meant, so a person or the agent has to pick.

## Configuration

Severity error. `[tool.inwards.rules]` can turn the rule off or make it a warning ([Configure rules](index.md#configure-rules)).

### Generated modules { #generated-modules }

Some modules exist only after a build step: `orders_pb2.py` and `orders_pb2_grpc.py` from protoc, `_version.py` from setuptools-scm or hatch-vcs. A developer's checkout has them and a fresh CI checkout doesn't. INW010 treats a module that `generated` in `[tool.inwards]` covers as existing, file or no file ([ADR-029](../05-ADR.md#adr-029-generated-modules-pass-inw010-protoc-and-version-modules-by-default)):

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards]
generated = ["*_pb2", "*_pb2_grpc", "_version", "shop.api.gen"]
```

- A pattern is a dotted module name, and each segment may use `*` and `?`. It matches whole segments anywhere in the resolved module name, as `ignore` does: `*_pb2` covers `shop.api.orders_pb2`, `_version` covers `shop._version`, `shop.api.gen` covers everything under `shop/api/gen/`. A wildcard never crosses a dot.
- There are no bracket sets. An empty segment, a character that can't be in a module name (`[` and `]` included) or a pattern made only of wildcards and dots (`*`, `*.*`) is a config error (exit 2). To turn INW010 off, use `ignore = ["INW010"]` in `[tool.inwards.rules]`.
- Without the key the list is `["*_pb2", "*_pb2_grpc", "_version"]`. Setting the key replaces that default, so list the default patterns too if you still want them, and `generated = []` turns it off.
- Only INW010 reads the key. The other rules still see a generated module that isn't on disk as missing: an outward import of one is still INW001, and INW006 names the nearest package that exists.

With the default, an import of a protoc module that isn't generated yet passes:

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.domain.orders_pb2 import Order
```

<!-- e2e -->

```sh
inwards check
```

Any other import can be suppressed on its line, with a reason:

```python
from shop.domain.legacy_rates import RATES  # inwards: ignore[INW010] reason="copied in by the deploy script, see #230"
```

## Known limitations

- `from shop.domain import pricing` passes when `shop/domain` is a package, since `pricing` could be a name its `__init__.py` defines ([ADR-025](../05-ADR.md#adr-025-inw010-probes-the-disk-for-existence-and-checks-only-the-module-part-of-an-import)).
- A made-up import whose name a `generated` pattern covers passes INW010, by default any `*_pb2`, `*_pb2_grpc` or `_version` module (`shop.api.payments_pb2` with no `payments.proto`). It still fails when the code runs. To catch those, set `generated = []` and run the generator before the check ([ADR-029](../05-ADR.md#adr-029-generated-modules-pass-inw010-protoc-and-version-modules-by-default)).
- An optional import behind `try/except ImportError` is reported.
- A namespace package shared with an installed distribution is reported as missing ([#161](https://github.com/SirCypkowskyy/inwards/issues/161)).
- Dynamic imports aren't checked for existence.
- The language server doesn't notice an `__init__.py` that starts extending its `__path__` until a file is created or deleted.
