# INW011 `dynamic-import`

## What it does

Reports a dynamic import, in a file in a layer, that reaches an outer layer: `importlib.import_module`, `__import__` (also as `builtins.__import__` and `importlib.__import__`), `runpy.run_module`, and import statements inside literal `exec`, `eval` or `compile` source. Loaders are followed through import aliases (`from importlib import import_module as im`), `name = loader` assignments, `getattr(m, "name")`, `m.__dict__["name"]` and `vars(m)["name"]`. A target made of literals joined with `+`, or an f-string whose fields are literals, is folded to its value.

In every layer but the outermost, a call whose target Inwards can't read is reported as unverifiable: a variable, an f-string field, a `\N{...}` escape, an argument behind `*args` or `**kwargs`, a relative `import_module` whose `package` isn't known, or `exec` or `eval` of a non-literal source. The outermost layer may reach every layer, so there is nothing to verify there, and that is where plugin loaders and composition roots belong. Bytes passed to `exec` or `compile` under a declared encoding Inwards can't read are reported as unchecked, in any layer.

## Why is this bad

Once [INW001](INW001.md) catches imports in functions and behind `TYPE_CHECKING`, the next cheapest dodge is a call: `importlib.import_module("shop.infrastructure.db")` is the same dependency with no import statement for a checker to see. When that is blocked too, putting the module name in a variable is the next step. INW011 reports both, and the fix names the loader as the problem, because rebuilding the name at runtime or switching to another loader only hides the dependency ([ADR-015](../05-ADR.md#adr-015-check-literal-dynamic-imports-as-inw011), [ADR-026](../05-ADR.md#adr-026-report-unreadable-dynamic-import-targets-in-inner-layers)).

## Example

With the layers from [INW001](INW001.md#example), the domain loads the infrastructure at runtime:

<!-- e2e -->

```python title="shop/domain/order.py"
import importlib


def repository():
    return importlib.import_module("shop.infrastructure.db")
```

<!-- e2e -->

```sh
inwards check
```

<!-- e2e -->

```text
shop/domain/order.py:5:12: INW011 Layer "domain" imports "shop.infrastructure.db" from outer layer "infrastructure" through a dynamic import (importlib.import_module). Allowed direction: domain <- application <- infrastructure.
  fix: Remove the dynamic import and depend on an abstraction owned by "domain" instead of "shop.infrastructure.db".
    1. Delete `importlib.import_module("shop.infrastructure.db")`. A dynamic import is still a dependency: building the module name at runtime or moving it to another loader hides it instead of removing it.
    2. Declare a typing.Protocol in `shop.domain` (for example `shop.domain.ports`) that describes only what this module needs from `db`.
    3. Type this module against that Protocol and receive the implementation through a constructor or function parameter.
    4. Make the class in "infrastructure" satisfy the Protocol, and wire it in the outermost layer (the composition root).
  docs: https://sircypkowskyy.github.io/inwards/rules/INW011/
```

With the module name in a variable, the target can't be checked:

<!-- e2e -->

```python title="shop/domain/order.py"
import importlib


def load(name: str):
    return importlib.import_module(name)
```

<!-- e2e -->

```sh
inwards check
```

<!-- e2e -->

```text
shop/domain/order.py:5:12: INW011 Layer "domain" makes a dynamic import (importlib.import_module) with an argument Inwards can't read, such as a variable, an f-string field or *args, so Inwards can't verify that it points toward inner layers.
  fix: Name the target with string literals, or move the dynamic import to the outermost layer "infrastructure".
    1. If the module is fixed, replace `importlib.import_module(name)` with an import statement, or pass the loader only string literals (no variables, f-string fields, \N{...} escapes or *args) so Inwards can check it.
    2. If the module is chosen at runtime (plugins, settings), move the loader to the outermost layer "infrastructure" (the composition root) and pass what it loads into this module as a parameter.
    3. Type that parameter against a typing.Protocol declared in `shop.domain` (for example `shop.domain.ports`).
  docs: https://sircypkowskyy.github.io/inwards/rules/INW011/
```

Fixed: the loader moves to the outermost layer, and the domain takes what it loads as a parameter typed against its own port.

<!-- e2e -->

```python title="shop/domain/ports.py"
from typing import Protocol


class Orders(Protocol):
    def total(self, order_id: int) -> int: ...
```

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.domain.ports import Orders


def total(orders: Orders, order_id: int) -> int:
    return orders.total(order_id)
```

<!-- e2e -->

```python title="shop/infrastructure/plugins.py"
import importlib


def load(name: str):
    return importlib.import_module(name)
```


## How to fix

1. If the module is fixed, replace the call with an import statement, or pass the loader only string literals so Inwards can check it. An import statement that points outward is then [INW001](INW001.md)'s finding, with the usual fix: a port in the inner layer.
2. If the module is chosen at runtime (plugins, settings), move the loader to the outermost layer and pass what it loads into the inner module as a parameter.
3. Type that parameter against a `typing.Protocol` declared in the inner layer.

## Fix safety

No automatic fix (`autofix: false`). Replacing a runtime loader changes how the program is wired, which needs review.

## Configuration

Severity error, for unverifiable targets too: a warning would pass the hook and the Stop gate, and the dodge would land. `[tool.inwards.rules]` can turn the rule off or make it a warning ([Configure rules](index.md#configure-rules)). A reviewed loader can be suppressed on the call's first line:

```python
importlib.import_module(  # inwards: ignore[INW011] reason="plugin loader, reviewed in #230"
    "shop.infrastructure.plugins",
)
```

## Known limitations

- Constant targets that aren't literals (a module-level `TARGET = "..."`, `str.format`, `%`) are reported as unverifiable instead of being read ([#79](https://github.com/SirCypkowskyy/inwards/issues/79)).
- Loaders reached through a walrus, tuple assignment, class or instance attributes, `functools.partial`, a name bound inside `exec`, or an object (`print.__self__.exec`) are missed, and so are other loading APIs: `pkgutil.resolve_name`, `importlib.util.find_spec` with `exec_module`, `SourceFileLoader(...).load_module()` ([#79](https://github.com/SirCypkowskyy/inwards/issues/79)).
- In the outermost layer an unverifiable call isn't reported, so it can reach first-party code outside every layer ([INW006](INW006.md)) unseen.
- `exec`, `eval`, `compile` and `__import__` with a literal source always count as the builtins, so after `from re import compile`, `compile("from shop.infrastructure import x")` is reported.
- A bare `exec` or `eval` with a computed source is skipped only when the code surely rebinds the name at the call, so `def eval(model, loader)` in training code isn't reported. The builtin passed in as an argument is missed, and some rebindings (a comprehension variable, a `match` capture) are still reported.

[Known limitations](../03-Architecture-C4.md#known-limitations) in chapter 3 has the full list.
