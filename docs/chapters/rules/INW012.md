# INW012 `thin-endpoint`

## What it does

Opt-in, and a warning by default. Reports an HTTP endpoint that does the work itself instead of handing it to a use case. One finding per endpoint, on its `def` line, lists every signal that tripped, with numbers. The counts include the helpers the endpoint calls in its own module, and the finding names each one:

| Signal | Default | What counts |
|---|---|---|
| `max-statements` | 10 | Statements in the body, nested ones included. The docstring doesn't count, and neither does a guard (`if <cond>: raise HTTPException(...)`, or `abort(404)` in Flask) or an `except` handler that only raises an HTTP error: mapping errors to HTTP is the endpoint's job. |
| `max-branches` | 2 | `if` and `elif`, `case` clauses and `except` handlers, guards left out. |
| `max-nesting` | 2 | How many compound statements (`if`, `for`, `while`, `try`, `with`, `match`) nest inside each other. |
| `allow-loops` | `false` | `for` and `while` in the body. Comprehensions are allowed (`allow-comprehensions = true`), since `[ItemOut.from_orm(i) for i in items]` shapes a response. |
| `deny-calls` | see below | Calls whose qualified name matches a pattern, through imports and aliases: `requests.*`, `httpx.*`, `aiohttp.*`, `urllib.request.*`, `smtplib.*`, `boto3.*`, `redis.*`, `sqlalchemy.*`, `psycopg*.*`, `asyncpg.*`, `celery.*`, `django.db.connection.*`. |
| `deny-receiver-types` | the SQLAlchemy and SQLModel sessions | Method calls on a parameter whose annotation resolves to one of these types: `db.execute`, `session.add`, `db.commit`. The annotation may be plain, `Annotated[T, ...]`, `Optional[T]`, `T \| None`, or an alias defined in the same file. |
| `deny-receiver-params` | none | The same, by parameter name, for untyped code (`db`, `session`). Off by default because it guesses. |
| `delegate-to` | unset | Layer names or module prefixes and selectors. When set, the endpoint must call at least one function, or a method of a parameter, that comes from there. |

An endpoint is a function or method that one of these marks:

- **FastAPI and Starlette:** a path operation decorator (`@router.get`, `post`, `put`, `patch`, `delete`, `head`, `options`, `trace` or `api_route`) on a name the file binds to `FastAPI(...)` or `APIRouter(...)`, or imports; or a registration away from the function: `router.add_api_route(path, handler)`, Starlette's `Route(path, handler)` and FastAPI's `APIRoute(path, handler)`, with the handler as the second argument or `endpoint=`.
- **Flask:** `@<x>.route`, `get`, `post`, `put`, `patch` or `delete` on a name the file binds to `Flask(...)` or `Blueprint(...)`, or imports; `add_url_rule(rule, endpoint, view_func)` with the handler as the third argument or `view_func=`; the methods named after HTTP verbs of a `MethodView` subclass, and `dispatch_request` of a `View` subclass.
- **Litestar:** `@get`, `@post`, `@put`, `@patch`, `@delete`, `@head`, `@route` and `HTTPRouteHandler` imported from `litestar` (or `litestar.handlers`), on functions and on `Controller` methods alike.
- **Django and DRF:** `@api_view` and `@action`; the methods named after HTTP verbs or ViewSet actions (`list`, `create`, `retrieve`, `update`, `partial_update`, `destroy`) of a subclass of a view class from `django.views`, `rest_framework.views`, `rest_framework.generics` or `rest_framework.viewsets` (`View`, `APIView`, `GenericAPIView`, `ListCreateAPIView`, `ModelViewSet` and the rest); a function a `path(route, view)` or `re_path(...)` call in the file names; and, only in a module `modules` names, a module-level function whose first parameter is `request`, since "a function that takes a request" is too broad anywhere else.
- **Your own:** a configured decorator (`decorators`), and the HTTP verb and ViewSet action methods of a subclass of a configured base class (`base-classes`).

`frameworks` picks the recognisers; by default every framework the file mentions is on. A view class's base can come from the same file or another first-party module (`class OrdersView(BaseView)` where `BaseView` extends `APIView`). Websocket routes are left out: a receive loop is their job.

Files are checked whatever layer they are in; `modules` narrows the rule to some of them.

## Why is this bad

Agents put the whole feature in the route handler: the query, the loop over rows, the call to a payment API, the email. The tests pass, and the service layer the project set up stays empty. Import rules can't see it: in the usual layouts the router and the service sit in the same layer, and a handler gets a database session through `Depends(get_db)` without importing SQLAlchemy at all. The style guides agree ("Don't do business logic in your API", HackSoft's Django Styleguide), and generic linters only measure size: Ruff's PLR0915 applies one limit of 50 statements to every function and doesn't know which one is an endpoint or what it calls.

```python title="store/api/orders.py"
from typing import Annotated

import httpx
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from store.api.db import Customer, OrderRow, Product, get_db

router = APIRouter()


@router.post("/orders", status_code=201)
async def create_order(body: dict, db: Annotated[AsyncSession, Depends(get_db)]) -> dict:
    customer = await db.scalar(select(Customer).where(Customer.id == body["customer"]))
    if customer is None:
        raise HTTPException(404, "customer not found")
    total = 0
    for product_id, qty in body["lines"]:
        product = await db.get(Product, product_id)
        if product.stock < qty:
            raise HTTPException(409, "out of stock")
        product.stock -= qty
        total += product.price * qty
    order = OrderRow(customer_id=customer.id, total=total)
    db.add(order)
    await db.commit()
    httpx.post("https://hooks.example.com/orders", json={"order": order.id})
    return {"id": order.id, "total": total}
```

Moving the body into a helper in the same module doesn't hide it. The helper's statements, loops and calls count as the endpoint's, its `db` parameter takes the session type of the argument passed to it, and the finding names the helper:

## How it works

A text pre-filter runs first: a file that mentions none of the recognised frameworks (`fastapi`, `FastAPI`, `APIRouter`, `starlette` or `add_api_route` for FastAPI, `flask`, `litestar`, `django` or `rest_framework`) and not the last part of a configured decorator or base class is never parsed. With `frameworks` set, only the listed frameworks' words count, and the other recognisers don't run. A file that passes gets one parse of its own, and another module is read and parsed only when a registration in the file names a handler there.

- **Endpoints** come from decorators, at any depth. A FastAPI or Flask route decorator counts on a name the file binds to an app or router, or on an imported name, as in the FastAPI model the FAPI rules read; Litestar's and DRF's decorators count by their qualified name. A method's finding names it `Class.method`. A `decorators` entry matches the qualified name of what the decorator calls or names, with `*` and `?` as wildcards (`*` also crosses dots, as in fnmatch).
- **View classes** count by their bases: a framework view class, a `base-classes` entry, or a class whose own bases lead to one, in the same file or, through the project index, in another first-party module (a cycle of bases ends the search). Only methods defined in the class's own body count; inherited handlers and hooks such as `get_queryset` or `perform_create` don't.
- **Registered handlers** come from `add_api_route` and `add_url_rule` on an app or router (bound in the file or imported), and from `Route(...)`, `APIRoute(...)`, `path(...)` and `re_path(...)` calls. A handler defined at module level in the same file is reported on its `def` line, like a decorated one. A handler from another first-party module is found through the project index, following re-exports such as `from .views import create_order` in an `__init__.py`, and reported on the registration, since that is the file being checked: the message names the handler's file and line. A handler that is already an endpoint in its own module (a route decorator marks it there) is left to that module's check, so it isn't reported twice.
- **Metrics** come from one walk over the body. A nested `def`, `class` or `lambda` counts as one statement, and what is inside it is its own business.
- **Helpers** are module-level functions of the endpoint's own module that it calls by name (`_create_order_impl(body)`). Their bodies count as the endpoint's: statements, branches, loops and comprehensions add up, nesting is the deepest of any one body, and their calls are sorted like the endpoint's own, `delegate-to` included, so a helper that calls the use case counts as the endpoint calling it. A helper's helpers are followed too, up to three calls deep from the endpoint, and each function counts once per endpoint, which also stops recursion. A helper's parameter reads its own annotation, or, without one, the type of the endpoint's parameter passed to it. One finding per endpoint names every helper it counted, with its line; helpers get no finding of their own, and a helper two endpoints call counts in both. Not followed: a `Depends(...)` target (FastAPI calls it, the endpoint doesn't), another endpoint, a nested function, a function imported from another module, and a method.
- **Calls** are qualified through the file's imports, so `from httpx import post as send` makes `send(...)` a call to `httpx.post`. A call on a parameter reads the parameter's annotation and its `Depends(...)` target: `place_order(...)` with `place_order: Annotated[PlaceOrder, Depends(get_place_order)]` reaches both `PlaceOrder` and `get_place_order`.
- **`delegate-to`** asks which layer owns each name a call reaches (a layer name), or whether a prefix or selector matches it.
- **Fix steps** name the `delegate-to` target (for a selector, the module it stands for in the endpoint's package: the part up to its last wildcard is matched against the endpoint's module, and the literal rest is appended), the session calls to move behind a repository (in the layer the session's type or dependency comes from, when a layer other than the endpoint's own owns it), and the denied calls to move into an adapter.

## How to fix

1. Move the loop and the business rules into a function in the `delegate-to` layer (a use case or a service) that takes plain arguments and returns a domain object.
2. Move the session calls behind a repository, and give the use case a Protocol it can call.
3. Move outgoing calls (HTTP, mail, queues) into an adapter or a background task that the use case triggers.
4. In the endpoint, keep only what HTTP needs: read the request, call the use case, map its errors to HTTP (`HTTPException`, `abort()`, `Http404` or a DRF exception), and return the response.

Don't split the endpoint into helpers in the same module to get under the limits: INW012 counts them as part of the endpoint, and the work would still live in the HTTP layer.

## Fix safety

No automatic fix (`autofix: false`). Where the logic goes, and what the use case's interface looks like, is a design decision.

## Configuration

Severity warning, so a finding doesn't fail `inwards check` or block the Stop gate; `severity = { INW012 = "error" }` makes it blocking. Opt-in: turn it on with `extend-select`. The options live in `[tool.inwards.rules.thin-endpoint]` ([options tables](index.md#opt-in-rules)), and an agent can't edit them (the config guard covers the whole table). The `fastapi` preset of [`inwards init`](../guides/install.md#a-new-project-start-from-a-preset) turns INW012 on as a warning with `delegate-to = ["domain.service"]`, the `service` module of every domain package:

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards.rules]
extend-select = ["INW012"]

[tool.inwards.rules.thin-endpoint]
modules = ["shop.*.api"]                    # optional: only these modules
max-statements = 10                         # false turns a threshold off
max-branches = 2
max-nesting = 2
allow-loops = false
allow-comprehensions = true
deny-calls = ["requests.*", "httpx.*"]      # replaces the default list
extend-deny-calls = ["shop.integrations.stripe.*"]  # adds to it
deny-receiver-types = ["sqlalchemy.orm.Session", "sqlalchemy.ext.asyncio.AsyncSession"]
deny-receiver-params = ["db"]               # untyped code
delegate-to = ["application"]               # layer names, prefixes or selectors
decorators = ["shop.http.endpoint"]         # in-house endpoint decorators
frameworks = ["fastapi", "django"]          # default: whatever the file mentions
base-classes = ["shop.http.Resource"]       # in-house view base classes
```

- `max-statements`, `max-branches`, `max-nesting`: an integer from 0 to 1000, or `false` to turn the check off.
- `deny-calls`, `extend-deny-calls`, `deny-receiver-types`, `decorators`, `base-classes`: qualified names with `*` and `?` as wildcards. `deny-calls = []` turns the call check off; `deny-receiver-types` replaces its default list (`sqlalchemy.orm.Session`, `sqlalchemy.orm.session.Session`, `sqlalchemy.ext.asyncio.AsyncSession`, `sqlalchemy.ext.asyncio.session.AsyncSession`, `sqlmodel.Session`, `sqlmodel.ext.asyncio.session.AsyncSession`).
- `delegate-to`: a layer name from `layers`, or a module prefix or selector in the grammar of `layers[].modules`. An entry that is neither is a config error.
- `frameworks`: distinct entries from `fastapi` (Starlette included), `flask`, `litestar` and `django` (DRF included). Unset, a framework's recogniser runs in every file that mentions it.
- Django's ORM: a manager call such as `Order.objects.filter(...)` isn't denied by default, since it is how Django code reads the database and a default would flag every view. To treat it as database work in a view, add `extend-deny-calls = ["*.objects.*"]`. Django's raw `connection.cursor()` is in the default list.

Every finding can be suppressed inline with `# inwards: ignore[INW012] reason="..."` on the line it is reported on: the `def` line, or for a handler from another module, the line of the registration.

## Known limitations

- **Business logic or presentation.** An endpoint that builds a CSV, paginates or sets cache headers is long for good reasons. The finding lists numbers, not a verdict; raise a threshold or narrow `modules`.
- **Simple CRUD apps.** Some teams choose `db.get(...)` in the handler on purpose. That is why the rule is opt-in.
- **Indirection.** `s = db; s.execute(...)`, a session passed through `**kwargs`, a type alias imported from another module and string annotations all hide calls. Helpers are followed only in the endpoint's own module and only three calls deep; a helper imported from another module, a method on a class, and a function stored in a variable or a dict aren't followed.
- **Handlers registered from another module** are reported where they are registered, not where they are defined. A per-edit check of the handler's own module (the PostToolUse hook after an edit there) doesn't see the registration; the whole check (`inwards check`, the Stop gate) and an edit of the registering file do.
- **Framework detection is by text.** A file is read for a framework only when it mentions it, so a blueprint imported from a first-party module (`from shop.web import bp`) in a file that never says `flask` isn't recognised, and a view base from another module is followed only in a file that mentions Django, DRF or Flask. List such bases in `base-classes`.
- **Not linked:** `include(...)` in `urls.py`, `as_view()` in a registration (the class's own methods count instead), Starlette's `Mount` and `add_route`, Flask's `register_blueprint`, Litestar's `Router(route_handlers=[...])` for a function with no decorator, and a handler passed through a variable.
- **Inherited handlers.** A generic view that only overrides hooks (`get_queryset`, `perform_create`, `get_serializer_class`) isn't checked: the hooks aren't request handlers, and the handlers live in the framework.
- **Guards.** An `HTTPException` (any framework's, by its name), Werkzeug's, Litestar's and DRF's exceptions, Django's `Http404` and `PermissionDenied`, and Flask's `abort(...)` count as mapping an error to HTTP. A first-party subclass raised in a guard is counted as a statement and a branch.
- **Custom decorators** that wrap a handler and do the work themselves aren't read.
- **False positives:** a method named `execute` on a service typed as `Session` by mistake. A comprehension that does I/O counts as allowed, though the calls inside it are still checked.
- **Thresholds** are a first guess, not yet tuned on a corpus; thresholds that are too tight push agents to split handlers into meaningless helpers.
