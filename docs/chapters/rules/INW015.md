# INW015 `construct-only-in`

## What it does

Opt-in, and an error when on. You name a role, the modules only the composition root may build, such as the outbound adapters, and the modules allowed to build them. INW015 then reports two things in every other module a layer owns:

- **An import of a role module that runs.** A plain import, a `from` import, a relative or star import, and an import inside a function all count; the finding sits on the imported name. An import inside an `if TYPE_CHECKING:` (or `if typing.TYPE_CHECKING:`) block doesn't count: it never runs, so it builds nothing.
- **A call that builds a class of the role, reached another way.** `SqlOrderRepo()` after `from store.adapters import SqlOrderRepo`, where `store/adapters/__init__.py` re-exports it, or `store.adapters.outbound.sql.SqlOrderRepo()` after `import store.adapters`. The finding sits on the call. A call whose name comes from an import INW015 already reports isn't reported again.

The role's own modules may import each other, and so may the modules `allowed-in` lists. A module no layer owns, such as a test or a script, isn't checked: tests build adapters on purpose.

## Why is this bad

In ports and adapters, the inner layers own a port (an abstract class or a `Protocol`), an outbound adapter implements it, and the composition root (`main.py`, `di.py`) builds the adapter and hands it to whoever needs the port. When an inbound adapter, such as a REST controller, builds `SqlOrderRepo()` itself, that wiring is gone: the controller is tied to SQL, a test can't swap in a fake, and the next agent copies the pattern into every route.

INW001 can't see it. Inbound and outbound adapters usually sit in the same layer, so the import doesn't point outward. INW003's public modules are about bounded contexts, not about who may build what.

  { name = "application", modules = ["store.application"] },

  { name = "bootstrap", modules = ["store.main"] },

[tool.inwards.rules]

if TYPE_CHECKING:

## How it works

INW015 runs on a module when the rule is on for it (`modules`), a layer owns it, and it is neither in `role` nor in `allowed-in`. A file without the word `import` is never parsed; any other gets one parse of its own.

- **Imports.** Every import statement, nested ones included, is resolved the way INW001 resolves it, and the project's module index says which first-party module it lands in. An import that lands in a role module and isn't in the body of an `if TYPE_CHECKING:` or `elif TYPE_CHECKING:` branch is reported. The `else` branch runs, so it counts.
- **Calls.** A call whose callee's last name starts with a capital letter, as Python names classes, is qualified through the file's imports and followed through the module index, across up to four re-exports, to a top-level `class`. If that class is defined in a role module, the call is reported. Only modules in the role, in `allowed-in`, and packages above the role (whose `__init__.py` may re-export it) are read, each once per checked file.
- **INW001 first.** An import that points outward to another layer gets INW001 alone, whose fix already says to depend on a port. With INW001 off for the module, INW015 reports it.

## How to fix

1. Depend on the port the adapter implements, not on the adapter.
2. Take the implementation as a constructor or function parameter. In a FastAPI route or dependency, use `Depends()` on a provider whose return type is the port.
3. Build the adapter in the composition root and pass it in from there.

## Fix safety

No automatic fix (`autofix: false`). Moving construction into the composition root changes constructors and call sites in more than one module.

## Configuration

Severity error. Opt-in: turn it on with `extend-select`. The `clean` and `hexagonal` presets of [`inwards init`](../guides/install.md#a-new-project-start-from-a-preset) turn INW015 on as a warning, with their driven adapters (`app.infrastructure` or `app.adapters.outbound`) as `role` and `app.bootstrap` as `allowed-in`. The options live in `[tool.inwards.rules.construct-only-in]` ([options tables](index.md#opt-in-rules)):

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards.rules]
extend-select = ["INW015"]

[tool.inwards.rules.construct-only-in]
role = ["app.adapters.outbound", "app.*.gateways"] # required: the guarded modules
allowed-in = ["app.di", "app.main"]                # the composition root
modules = ["app.adapters"]                         # optional: only report here
```

- `role` (required): module prefixes or selectors, as in a layer's `modules`, of the modules only the composition root may import and build. A prefix covers the package and everything below it. A table without `role` is a config error.
- `allowed-in`: module prefixes or selectors of the composition root, which may import the role and build its classes. Unset, only the role's own modules may.
- `modules`: as for every rule, the modules INW015 reports in. Unlike in most rules, it doesn't name the role: that is `role`.

A single import can be suppressed with a reason on its line: `# inwards: ignore[INW015] reason="..."`.

A [template](../guides/configuration.md#template-rules) can turn INW015 on for one of its roles: `outbound = { construct-only-in = { allowed-in = ["app.di"] } }` puts the role's modules in `role`, not in `modules`, so the role is what the rule guards.

## Known limitations

- **Classes only, by name.** The call form follows a callee whose name starts with a capital letter, so a factory function (`make_repo()`) or a lowercase class reached through a re-export isn't followed. Its import, when it imports a role module directly, is still reported.
- **What hides a class.** A class assigned to another name (`Repo = SqlOrderRepo`), passed around as a value, or handed to `Depends(SqlOrderRepo)` through a re-export isn't followed. A direct import of it is reported all the same.
- **Re-exports.** Up to four re-exports are followed, and only through the role, `allowed-in`, and the packages above the role.
- **Modules no layer owns** aren't checked at all, so code outside your layers can build adapters freely.
- **One finding per import, not per use.** Fixing the import fixes every use of it.
- **Exceptions of the role aren't reported.** `from <role module> import StorageError` (a name ending in `Error`, `Exception` or `Warning`), and a call that builds such a class through a re-export, builds no adapter: code outside the role catches the error or maps it to an HTTP status. A name that only looks like an exception passes too.
- **Measured on the corpus** ([#182](https://github.com/SirCypkowskyy/inwards/issues/182), [chapter 6](../06-Constraints-and-Quality.md#precision-of-the-opt-in-rules)) with `role` set to fastapi-clean-example's `app.outbound` and python-ddd's `infrastructure` packages: 48 findings before the exception rule, 17 after, every one looked at. 15 of the 17 are true positives (an application query importing an ORM model from infrastructure, an inbound handler importing an outbound handler class). The other 2: a constant imported from an adapter (`STAGED_COOKIE`), and a test module a layer owns ([#362](https://github.com/SirCypkowskyy/inwards/issues/362)).
