# INW020 `adapter-conformance`

## What it does

Opt-in, and an error when on. Checks that every public top-level class of an adapter module declares the port it implements with a conformance line: an annotated assignment in a module-level `if TYPE_CHECKING:` (or `if typing.TYPE_CHECKING:`) block whose value builds the class or is the class.

```python
if TYPE_CHECKING:
    _: OrderRepository = SqlOrderRepository(...)    # or
    _: type[OrderRepository] = SqlOrderRepository
```

The target name is free; `_` is the convention. Any arguments go, `...` included, and `SqlOrderRepository[int](...)` counts too. Three things are reported:

- **No conformance line**, on the class's name. The example line in the message names the port when the module imports exactly one class from a port module, and says `<Port>` otherwise.
- **A line that runs**, on the line: the same annotated assignment at module level outside `if TYPE_CHECKING:`, the `else` branch included. It builds the adapter, or needs the port imported, every time the module is imported.
- **An annotation that names no port**, on the annotation: with `ports` set, a class that isn't from one of those modules; with or without it, `Any` or `object`, which accept any value.

A class needs no line when its name starts with `_`, when it is a port itself (a `Protocol` or an ABC), or when it is a record: an exception, an enum, a Pydantic model, a named tuple, a typed dict or a dataclass. See [Configuration](#configuration).

Without `modules`, the rule checks every module with an `adapters` segment in its name: `shop.adapters`, `shop.adapters.outbound.orders`. Set `modules` to check other modules instead.

## Why is this bad

A port here is a `typing.Protocol`, and an adapter implements it by having its members; subclassing the protocol is "not necessary for the sake of type-checking" ([typing spec, Protocols](https://typing.python.org/en/latest/spec/protocol.html#explicitly-declaring-implementation)). That leaves nothing in the adapter's module that says which port it implements, so nothing checks it until the composition root passes the adapter where the port is expected, if it does. An agent that renames a port method, or adds one, finds out at run time.

The conformance line closes that gap. `TYPE_CHECKING` is `False` at runtime and assumed `True` by static type checkers ([`typing.TYPE_CHECKING`](https://docs.python.org/3/library/typing.html#typing.TYPE_CHECKING)), so the line builds nothing and is still checked: assignability to a protocol is structural, and ty reports a value that doesn't fit the declared type as [`invalid-assignment`](https://docs.astral.sh/ty/reference/rules/#invalid-assignment), as mypy and Pyright do. A variable annotated `type[Port]` accepts a concrete class whose instances implement the protocol ([type[] and class objects vs protocols](https://typing.python.org/en/latest/spec/protocol.html#type-and-class-objects-vs-protocols)). INW020 checks that the line is there; the type checker checks what it says ([ADR-046](../05-ADR.md#adr-046-structural-ports-conformance-lines-and-private-modules-are-opt-in-rules-cqrs-slices-a-template)).

## How it works

A file is parsed only when INW020 is on for its module, the module is an adapter module, and its text has the word `class`. One parse per such file; no other module is read, so the per-edit hook, the editor and MCP report it on the edit that breaks it.

- **Classes.** The top-level classes whose name doesn't start with `_`. A class is exempt when an allowed decorator or base is among its own, when a base is a same-file class that is exempt that way, or when it lists `Protocol`, `abc.ABC` or `metaclass=abc.ABCMeta`.
- **Names** are qualified through the file's imports, as for [INW014](INW014.md): `import typing` with `typing.TYPE_CHECKING`, aliased imports and `typing_extensions` all count. A name the file doesn't import is a builtin, spelled bare (`Exception`, `object`).
- **Lines.** An annotated assignment directly at module level, or directly in a branch of a module-level `if`. Its value is `Name(...)` or `Name[...](...)` with any annotation, or a bare `Name` under `type[...]` (`typing.Type[...]` too), where `Name` is a class the rule checks. A line in the body of `if TYPE_CHECKING:` or `elif TYPE_CHECKING:` is for the type checker; any other one runs.
- **Ports.** With `ports` set, the annotation's head (`Repo` of `Repo[int]`) must resolve to a CapWords name defined in one of those modules. Without it, the port in a message is the one CapWords name the module imports from a module with a `ports` segment.
- **One finding per problem.** A class with a line that runs, or with a line whose annotation names no port, isn't reported as having no line as well.

## How to fix

1. Import the port under `if TYPE_CHECKING:`.
2. Add `_: Port = Adapter(...)`, or `_: type[Port] = Adapter`, in an `if TYPE_CHECKING:` block at the end of the module; one line per port for a class that implements several.
3. If the class is a helper, not an adapter, rename it `_Name` or move it out of the adapter module. If it is a record on a base of the project's own, ask whoever owns the config to add that base to `extend-allow-bases`.

## Fix safety

No automatic fix (`autofix: false`). Which port a class implements isn't in the code; that is what the line says.

## Configuration

Severity error. Opt-in: turn it on with `extend-select`. The `clean` and `hexagonal` presets of [`inwards init`](../guides/install.md#a-new-project-start-from-a-preset) turn INW020 on as a warning, with `modules` set to the driven adapter layer and `ports` to `application.ports`. The options live in `[tool.inwards.rules.adapter-conformance]` ([options tables](index.md#opt-in-rules)):

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards.rules]
extend-select = ["INW020"]

[tool.inwards.rules.adapter-conformance]
modules = ["shop.infrastructure"]       # optional: the adapter modules
ports = ["shop.application.ports"]      # optional: annotations must name a class from these
extend-allow-bases = ["shop.kit.Schema"]
```

- `modules`: module prefixes or selectors, as in a layer's `modules`. Set, INW020 checks the modules they match instead of the ones with an `adapters` segment.
- `ports`: module prefixes or selectors of the port modules. Set, a line's annotation must name a class from one of them, and the message names the one the module imports from them.
- `allow-bases`, `extend-allow-bases` and `allow-decorators`: as for [INW014](INW014.md#configuration), with the same defaults (exceptions, `pydantic.BaseModel`, `NamedTuple`, `TypedDict`, `enum.*`; dataclass, pydantic and attrs decorators).
- `check-tests`: `true` makes INW020 report in test modules too, which it skips by default ([options tables](index.md#opt-in-rules)).

To accept one finding, suppress it on the line it points at: `# inwards: ignore[INW020] reason="..."` on the `class` line, the conformance line or the annotation's line.

A [template](../guides/configuration.md#template-rules) can turn INW020 on for one of its roles: `adapters = { adapter-conformance = true }` sets `modules` to the role's modules.

## Known limitations

- **An adapter or a helper.** The rule can't tell them apart: every public class in an adapter module needs a line. A helper needs an underscore, an allowed base, or a narrower `modules`.
- **Project bases.** A Pydantic model on a project's own base (`class Cursor(Schema)` with `Schema` from `polar.kit.schemas`) is reported until the base is in `extend-allow-bases`: the base is read by name, not followed.
- **What the line says.** Whether the class matches the port is the type checker's job, and a project that doesn't run one gets a line nobody checks.
- **Lines read.** A line nested deeper than a branch of a module-level `if` (inside a `try`, or an `if` inside `if TYPE_CHECKING:`) isn't read. A string annotation (`_: "Port" = Adapter(...)`) counts as a line but its port isn't checked.
- **CapWords ports.** The port in a message and the `ports` check take a CapWords name for a class and a lower-case one for a module, since no other file is read.
- **Measured on the corpus** (2026-10-11, the five repos of `bench/corpus.json`, the manifest layering plus `select = ["INW020"]`): 8 findings in fastapi-clean-example, its 8 adapters, which subclass their ports instead; 2 in Polar, its `StripeAdapter` and `StripeExtractionCursor`, a Pydantic model on the project's own `Schema` base; none in the other three, which have no `adapters` modules. No project in the corpus follows the convention yet, which is why the rule is opt-in.
