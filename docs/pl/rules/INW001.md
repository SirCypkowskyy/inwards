# INW001 `layer-dependency`

## Co robi { #what-it-does }

Zgłasza import, w pliku należącym do warstwy, własnego kodu, który należy do warstwy zewnętrznej. Warstwy w `[tool.inwards]` są wymienione od najbardziej wewnętrznej, a moduł może importować własną warstwę i wszystko, co wymieniono przed nią. [Warstwy sąsiednie](../guides/configuration.md#sibling-layers), zagnieżdżona tablica w `layers` albo `a | b` w rolach [szablonu](../guides/configuration.md#templates), też nie mogą importować jedna drugiej; komunikat mówi wtedy `from sibling layer`.

Liczy się każdy import w pliku: na najwyższym poziomie, wewnątrz funkcji lub klasy i za `if TYPE_CHECKING:` ([ADR-009](../05-ADR.md#adr-009-check-imports-wherever-they-appear)). Importy względne są rozwiązywane względem pakietu pliku, a `from shop import infrastructure` jest rozwiązywane do `shop.infrastructure`. Importami dynamicznymi (`importlib.import_module("shop.infrastructure.db")`) zajmuje się [INW011](INW011.md).

## Dlaczego to źle { #why-is-this-bad }

Import na zewnątrz wiąże warstwę wewnętrzną ze szczegółami, od których ma być niezależna: domeny nie da się już testować, czytać ani użyć ponownie bez kodu bazy danych. Agenci robią taką edycję często, bo zaimportowanie klasy, która już wykonuje zadanie, to najkrótsza droga do działającego kodu. Code review wyłapuje to późno, o ile w ogóle. Pierwsze, co agent próbuje zrobić ze zgłoszonym importem, to go ukryć, w funkcji albo za `TYPE_CHECKING`, więc reguła sprawdza też te miejsca, a poprawka mówi o tym wprost.

## Przykład { #example }

Warstwy tego przykładu, których używają też pozostałe strony reguł:

<!-- e2e -->

```toml title="pyproject.toml"
[tool.inwards]
layers = [
  { name = "domain",         modules = ["shop.domain"] },
  { name = "application",    modules = ["shop.application"] },
  { name = "infrastructure", modules = ["shop.infrastructure"] },
]
```

Domena sięga do infrastruktury po klasę, która rozmawia z bazą danych:

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.infrastructure.db import SqlOrders


def total(order_id: int) -> int:
    return SqlOrders().total(order_id)
```

<!-- e2e -->

```sh
inwards check
```

<!-- e2e -->

```text
shop/domain/order.py:1:36: INW001 Layer "domain" imports "shop.infrastructure.db.SqlOrders" from outer layer "infrastructure". Allowed direction: domain <- application <- infrastructure.
  fix: Depend on an abstraction owned by "domain" instead of "shop.infrastructure.db.SqlOrders".
    1. Delete `from shop.infrastructure.db import SqlOrders`. Do not move the import into a function or behind TYPE_CHECKING; Inwards checks those too.
    2. Declare a typing.Protocol in `shop.domain` (for example `shop.domain.ports`) that describes only what this module needs from `SqlOrders`.
    3. Type this module against that Protocol and receive the implementation through a constructor or function parameter.
    4. Make the class in "infrastructure" satisfy the Protocol, and wire it in the outermost layer (the composition root).
  docs: https://sircypkowskyy.github.io/inwards/rules/INW001/
```

Po poprawce domena ma własny port, a infrastruktura go implementuje.

<!-- e2e -->

```python title="shop/domain/ports.py"
from typing import Protocol


class Orders(Protocol):
    def total(self, order_id: int) -> int: ...
```

<!-- e2e -->

```python title="shop/domain/order.py"
from shop.domain.ports import Orders


def total(orders: Orders, order_id: int) -> int:
    return orders.total(order_id)
```

<!-- e2e -->

```python title="shop/infrastructure/db.py"
class SqlOrders:
    def total(self, order_id: int) -> int:
        return 0
```

<!-- e2e -->

```sh
inwards check
```

`SqlOrders` spełnia `Orders` strukturalnie, więc nie musi importować domeny. Korzeń kompozycji (composition root) w najbardziej zewnętrznej warstwie przekazuje `SqlOrders()` do `total`.

## Jak naprawić { #how-to-fix }

1. Usuń import. Przeniesienie go do funkcji, za `TYPE_CHECKING` albo do `importlib` tylko przenosi diagnostykę.
2. Zadeklaruj w warstwie wewnętrznej `typing.Protocol`, który opisuje tylko to, czego moduł potrzebuje.
3. Otypuj moduł względem tego Protocolu i przyjmuj implementację jako parametr konstruktora albo funkcji.
4. Niech klasa z warstwy zewnętrznej spełnia Protocol, a połącz je w najbardziej zewnętrznej warstwie.

Jeśli moduł naprawdę należy do warstwy wewnętrznej, przenieś go tam. Jeśli źle ustawione są same warstwy, decyduje użytkownik: poprawka nigdy nie każe agentowi edytować `[tool.inwards]`, a config guard go powstrzymuje.

## Bezpieczeństwo poprawki { #fix-safety }

Inwards nie ma automatycznej poprawki dla tej reguły (`autofix: false`). Powyższe kroki zmieniają projekt kodu, więc musi je wykonać człowiek albo agent, a wynik wymaga przeglądu.

## Konfiguracja { #configuration }

Poziom: błąd. `[tool.inwards.rules]` może wyłączyć regułę (`ignore = ["INW001"]`) albo zmienić ją w ostrzeżenie (`severity = { INW001 = "warning" }`); zobacz [Konfiguracja reguł](index.md#configure-rules). Żeby zaakceptować jeden import, wycisz go w jego linii:

```python
from shop.infrastructure.legacy import LegacyClient  # inwards: ignore[INW001] reason="old billing adapter, removed in #210"
```

Przy imporcie w nawiasach komentarz trafia do linii importowanej nazwy. Hooki Claude Code nie honorują wyciszenia, które agent dodał w trakcie sesji, chyba że ustawiono `agent-suppressions = "allow"` ([ADR-028](../05-ADR.md#adr-028-inline-suppressions-need-a-reason-and-an-agent-cant-add-one-by-default)).

W hookach Claude Code naruszenie blokuje edycję, która je dodaje, i Stop gate. Naruszenie, które plik miał już na starcie sesji, trafia do agenta jako kontekst, więc stary kod nie blokuje niezwiązanej edycji, z dwoma wyjątkami. Plik, który na starcie sesji był niezacommitowany, nieśledzony albo poza gitem i zbyt duży, żeby hooki zachowały jego kopię (ponad 512 KiB albo ponad limit 4 MiB takich plików), nie ma treści startowej, którą Inwards mógłby potwierdzić, więc każde naruszenie w nim blokuje, gdy tylko agent go zedytuje. Przy `stop-gate = "project"` Stop gate sprawdza cały projekt i blokuje każde naruszenie, którego nie akceptuje baseline, stare czy nowe. Szczegóły opisuje sekcja o [Stop gate](../04-AI-Integration.md#integrations-by-agent).

## Znane ograniczenia { #known-limitations }

- Przynależność do warstwy wynika tylko z prefiksu modułu. Globy takie jak `shop.*.domain` dla pionowych wycinków przyjdą z konfiguracją w wersji 2 ([#51](https://github.com/SirCypkowskyy/inwards/issues/51)).
- Nie ma wyjątku dla odwołań do warstwy zewnętrznej używanych tylko w typach ([ADR-009](../05-ADR.md#adr-009-check-imports-wherever-they-appear)).
- Importy wewnątrz własnego kodu, który nie należy do żadnej warstwy, nie są sprawdzane; ten kod zgłasza [INW006](INW006.md).
- W niejawnym pakiecie przestrzeni nazw (bez `__init__.py`) importy względne są rozwiązywane tak, jakby katalog był zwykłym pakietem.
- INW001 rozstrzyga warstwy po nazwie modułu, więc import przez dowiązanie symboliczne w warstwie, które wskazuje do innej warstwy, przechodzi tę regułę. Takie dowiązanie, a także dowiązanie wychodzące poza katalog `root`, zgłasza [INW006](INW006.md) w miejscu samego dowiązania ([ADR-013](../05-ADR.md#adr-013-real-paths-for-the-boundary-import-paths-for-module-names)).
