# INW012 `thin-endpoint`

## Co robi { #what-it-does }

Opt-in, domyślnie ostrzeżenie. Zgłasza endpoint HTTP, który sam wykonuje pracę, zamiast oddać ją przypadkowi użycia. Jedno zgłoszenie na endpoint, na linii jego `def`, wymienia z liczbami każdy sygnał, który przekroczył próg. Liczby obejmują funkcje pomocnicze, które endpoint wywołuje we własnym module, a zgłoszenie wymienia każdą z nich:

| Sygnał | Domyślnie | Co się liczy |
|---|---|---|
| `max-statements` | 10 | Instrukcje w ciele funkcji, razem z zagnieżdżonymi. Nie liczy się docstring ani warunek ochronny (`if <cond>: raise HTTPException(...)` albo `abort(404)` we Flasku), ani handler `except`, który tylko rzuca błąd HTTP: mapowanie błędów na HTTP to zadanie endpointu. |
| `max-branches` | 2 | `if` i `elif`, klauzule `case` i handlery `except`, bez warunków ochronnych. |
| `max-nesting` | 2 | Ile instrukcji złożonych (`if`, `for`, `while`, `try`, `with`, `match`) zagnieżdża się jedna w drugiej. |
| `allow-loops` | `false` | `for` i `while` w ciele. Wyrażenia listowe są dozwolone (`allow-comprehensions = true`), bo `[ItemOut.from_orm(i) for i in items]` kształtuje odpowiedź. |
| `deny-calls` | patrz niżej | Wywołania, których kwalifikowana nazwa pasuje do wzorca, przez importy i aliasy: `requests.*`, `httpx.*`, `aiohttp.*`, `urllib.request.*`, `smtplib.*`, `boto3.*`, `redis.*`, `sqlalchemy.*`, `psycopg*.*`, `asyncpg.*`, `celery.*`, `django.db.connection.*`. |
| `deny-receiver-types` | sesje SQLAlchemy i SQLModel | Wywołania metod na parametrze, którego adnotacja wskazuje jeden z tych typów: `db.execute`, `session.add`, `db.commit`. Adnotacja może być zwykła, `Annotated[T, ...]`, `Optional[T]`, `T \| None` albo aliasem zdefiniowanym w tym samym pliku. |
| `deny-receiver-params` | brak | To samo, po nazwie parametru, dla kodu bez typów (`db`, `session`). Domyślnie wyłączone, bo zgaduje. |
| `delegate-to` | nieustawione | Nazwy warstw albo prefiksy i selektory modułów. Gdy jest ustawione, endpoint musi wywołać co najmniej jedną funkcję albo metodę parametru, która stamtąd pochodzi. |

Endpoint to funkcja albo metoda, którą oznacza jedno z poniższych:

- **FastAPI i Starlette:** dekorator operacji ścieżki (`@router.get`, `post`, `put`, `patch`, `delete`, `head`, `options`, `trace` albo `api_route`) na nazwie, którą plik wiąże z `FastAPI(...)` albo `APIRouter(...)` albo importuje; albo rejestracja trasy z dala od funkcji: `router.add_api_route(path, handler)`, `Route(path, handler)` Starlette i `APIRoute(path, handler)` FastAPI, z handlerem jako drugim argumentem albo `endpoint=`.
- **Flask:** `@<x>.route`, `get`, `post`, `put`, `patch` albo `delete` na nazwie, którą plik wiąże z `Flask(...)` albo `Blueprint(...)` albo importuje; `add_url_rule(rule, endpoint, view_func)` z handlerem jako trzecim argumentem albo `view_func=`; metody nazwane jak metody HTTP w podklasie `MethodView` oraz `dispatch_request` w podklasie `View`.
- **Litestar:** `@get`, `@post`, `@put`, `@patch`, `@delete`, `@head`, `@route` i `HTTPRouteHandler` importowane z `litestar` (albo `litestar.handlers`), tak samo na funkcjach, jak na metodach `Controller`.
- **Django i DRF:** `@api_view` i `@action`; metody nazwane jak metody HTTP albo akcje ViewSet (`list`, `create`, `retrieve`, `update`, `partial_update`, `destroy`) w podklasie klasy widoku z `django.views`, `rest_framework.views`, `rest_framework.generics` albo `rest_framework.viewsets` (`View`, `APIView`, `GenericAPIView`, `ListCreateAPIView`, `ModelViewSet` i pozostałe); funkcja, którą wskazuje wywołanie `path(route, view)` albo `re_path(...)` w pliku; oraz, tylko w module, który wskazuje `modules`, funkcja z poziomu modułu, której pierwszy parametr to `request`, bo "funkcja, która przyjmuje żądanie" jest gdzie indziej zbyt szeroka.
- **Własne:** skonfigurowany dekorator (`decorators`) oraz metody nazwane jak metody HTTP i akcje ViewSet w podklasie skonfigurowanej klasy bazowej (`base-classes`).

`frameworks` wybiera rozpoznawanie; domyślnie włączony jest każdy framework, o którym plik wspomina. Klasa bazowa widoku może pochodzić z tego samego pliku albo z innego modułu projektu (`class OrdersView(BaseView)`, gdzie `BaseView` dziedziczy po `APIView`). Trasy websocket są pominięte: pętla odbioru to ich zadanie.

Pliki są sprawdzane bez względu na warstwę; `modules` zawęża regułę do części z nich.

## Dlaczego to źle { #why-is-this-bad }

Agenci wkładają całą funkcjonalność do handlera trasy: zapytanie, pętlę po wierszach, wywołanie API płatności, e-mail. Testy przechodzą, a warstwa serwisów, którą projekt przygotował, zostaje pusta. Reguły importów tego nie widzą: w typowych układach router i serwis leżą w tej samej warstwie, a handler dostaje sesję bazy danych przez `Depends(get_db)`, w ogóle nie importując SQLAlchemy. Przewodniki stylu mówią to samo ("Don't do business logic in your API", HackSoft Django Styleguide), a ogólne lintery mierzą tylko rozmiar: PLR0915 Ruffa stosuje jeden limit 50 instrukcji do każdej funkcji i nie wie, która jest endpointem ani co wywołuje.

```python title="store/api/orders.py"
from typing import Annotated

import httpx
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from store.api.db import Customer, OrderRow, Product, get_db

router = APIRouter()


@router.post("/orders", status_code=201)
async def create_order(body: dict, db: Annotated[AsyncSession, Depends(get_db)]) -> dict:
    customer = await db.scalar(select(Customer).where(Customer.id == body["customer"]))
    if customer is None:
        raise HTTPException(404, "customer not found")
    total = 0
    for product_id, qty in body["lines"]:
        product = await db.get(Product, product_id)
        if product.stock < qty:
            raise HTTPException(409, "out of stock")
        product.stock -= qty
        total += product.price * qty
    order = OrderRow(customer_id=customer.id, total=total)
    db.add(order)
    await db.commit()
    httpx.post("https://hooks.example.com/orders", json={"order": order.id})
    return {"id": order.id, "total": total}
```

## Jak działa { #how-it-works }

Najpierw działa filtr tekstowy: plik, który nie wspomina żadnego z rozpoznawanych frameworków (`fastapi`, `FastAPI`, `APIRouter`, `starlette` albo `add_api_route` dla FastAPI, `flask`, `litestar`, `django` albo `rest_framework`) ani ostatniej części skonfigurowanego dekoratora albo klasy bazowej, nigdy nie jest parsowany. Gdy `frameworks` jest ustawione, liczą się tylko słowa wymienionych frameworków, a pozostałe rozpoznawanie nie działa. Plik, który przejdzie filtr, dostaje jedno własne parsowanie, a inny moduł jest czytany i parsowany tylko wtedy, gdy rejestracja w pliku wskazuje w nim handler.

- **Endpointy** pochodzą z dekoratorów, na dowolnej głębokości. Dekorator trasy FastAPI albo Flaska liczy się na nazwie, którą plik wiąże z aplikacją albo routerem, albo na nazwie importowanej, tak jak w modelu FastAPI, który czytają reguły FAPI; dekoratory Litestara i DRF liczą się po kwalifikowanej nazwie. Zgłoszenie dla metody nazywa ją `Klasa.metoda`. Wpis `decorators` dopasowuje kwalifikowaną nazwę tego, co dekorator wywołuje albo nazywa, z `*` i `?` jako wildcardami (`*` przechodzi też przez kropki, jak w fnmatch).
- **Klasy widoków** liczą się po swoich klasach bazowych: klasie widoku frameworka, wpisie `base-classes` albo klasie, której własne klasy bazowe do nich prowadzą, w tym samym pliku albo, przez indeks projektu, w innym module projektu (cykl klas bazowych kończy szukanie). Liczą się tylko metody zdefiniowane we własnym ciele klasy; odziedziczone handlery i hooki, takie jak `get_queryset` albo `perform_create`, nie.
- **Zarejestrowane handlery** pochodzą z `add_api_route` i `add_url_rule` na aplikacji albo routerze (powiązanym w pliku albo importowanym) oraz z wywołań `Route(...)`, `APIRoute(...)`, `path(...)` i `re_path(...)`. Handler zdefiniowany na poziomie modułu w tym samym pliku jest zgłaszany na linii swojego `def`, jak udekorowany. Handler z innego modułu projektu jest wyszukiwany przez indeks projektu, z podążaniem za reeksportami, takimi jak `from .views import create_order` w `__init__.py`, i zgłaszany na rejestracji, bo to ten plik jest sprawdzany: komunikat podaje plik i linię handlera. Handler, który już jest endpointem we własnym module (oznacza go tam dekorator trasy), zostaje dla sprawdzenia tamtego modułu, więc nie jest zgłaszany dwa razy.
- **Metryki** pochodzą z jednego przejścia po ciele funkcji. Zagnieżdżone `def`, `class` albo `lambda` liczy się jako jedna instrukcja, a to, co jest w środku, to jej sprawa.
- **Funkcje pomocnicze** to funkcje z poziomu modułu endpointu, które endpoint wywołuje po nazwie (`_create_order_impl(body)`). Ich ciała liczą się jako ciało endpointu: instrukcje, gałęzie, pętle i wyrażenia listowe się sumują, zagnieżdżenie to najgłębsze z pojedynczych ciał, a ich wywołania są sortowane jak własne wywołania endpointu, łącznie z `delegate-to`, więc funkcja pomocnicza, która wywołuje przypadek użycia, liczy się tak, jakby wywołał go endpoint. Funkcje pomocnicze funkcji pomocniczych też są śledzone, do trzech wywołań w głąb od endpointu, a każda funkcja liczy się raz na endpoint, co zatrzymuje też rekurencję. Parametr funkcji pomocniczej czyta własną adnotację albo, gdy jej nie ma, typ parametru endpointu, który do niego trafia. Jedno zgłoszenie na endpoint wymienia każdą wliczoną funkcję pomocniczą z jej linią; funkcje pomocnicze nie dostają własnych zgłoszeń, a funkcja pomocnicza wywoływana przez dwa endpointy liczy się w obu. Nie są śledzone: cel `Depends(...)` (wywołuje go FastAPI, nie endpoint), inny endpoint, funkcja zagnieżdżona, funkcja importowana z innego modułu i metoda.
- **Wywołania** są kwalifikowane przez importy pliku, więc `from httpx import post as send` sprawia, że `send(...)` jest wywołaniem `httpx.post`. Wywołanie na parametrze czyta adnotację parametru i cel jego `Depends(...)`: `place_order(...)` z `place_order: Annotated[PlaceOrder, Depends(get_place_order)]` sięga i do `PlaceOrder`, i do `get_place_order`.
- **`delegate-to`** pyta, która warstwa jest właścicielem każdej nazwy, do której sięga wywołanie (dla nazwy warstwy), albo czy pasuje do niej prefiks lub selektor.
- **Kroki poprawki** nazywają cel z `delegate-to` (dla selektora moduł, który oznacza on w pakiecie endpointu: część do ostatniego wildcarda jest dopasowywana do modułu endpointu, a dosłowna reszta zostaje doklejona), wywołania sesji do przeniesienia za repozytorium (w warstwie, z której pochodzi typ albo zależność sesji, gdy jest nią warstwa inna niż warstwa endpointu) i zakazane wywołania do przeniesienia do adaptera.

## Jak naprawić { #how-to-fix }

1. Przenieś pętlę i reguły biznesowe do funkcji w warstwie z `delegate-to` (przypadek użycia albo serwis), która przyjmuje zwykłe argumenty i zwraca obiekt domeny.
2. Przenieś wywołania sesji za repozytorium i daj przypadkowi użycia Protocol, który może wywołać.
3. Przenieś wywołania na zewnątrz (HTTP, poczta, kolejki) do adaptera albo zadania w tle, które uruchamia przypadek użycia.
4. W endpoincie zostaw tylko to, czego potrzebuje HTTP: odczytaj żądanie, wywołaj przypadek użycia, zmapuj jego błędy na HTTP (`HTTPException`, `abort()`, `Http404` albo wyjątek DRF) i zwróć odpowiedź.

Nie dziel endpointu na funkcje pomocnicze w tym samym module, żeby zmieścić się w limitach: INW012 liczy je jako część endpointu, a praca nadal mieszkałaby w warstwie HTTP.

## Bezpieczeństwo poprawki { #fix-safety }

Brak poprawki automatycznej (`autofix: false`). To, dokąd trafia logika i jak wygląda interfejs przypadku użycia, to decyzja projektowa.

## Konfiguracja { #configuration }

Poziom: ostrzeżenie, więc zgłoszenie nie oblewa `inwards check` ani nie blokuje Stop gate; `severity = { INW012 = "error" }` czyni je blokującym. Opt-in: włącz regułę przez `extend-select`. Opcje są w `[tool.inwards.rules.thin-endpoint]` ([tabele opcji](index.md#opt-in-rules)), a agent nie może ich edytować (config guard obejmuje całą tabelę). Preset `fastapi` polecenia [`inwards init`](../guides/install.md#a-new-project-start-from-a-preset) włącza INW012 jako ostrzeżenie z `delegate-to = ["domain.service"]`, czyli modułem `service` każdego pakietu domeny:

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards.rules]
extend-select = ["INW012"]

[tool.inwards.rules.thin-endpoint]
modules = ["shop.*.api"]                    # optional: only these modules
max-statements = 10                         # false turns a threshold off
max-branches = 2
max-nesting = 2
allow-loops = false
allow-comprehensions = true
deny-calls = ["requests.*", "httpx.*"]      # replaces the default list
extend-deny-calls = ["shop.integrations.stripe.*"]  # adds to it
deny-receiver-types = ["sqlalchemy.orm.Session", "sqlalchemy.ext.asyncio.AsyncSession"]
deny-receiver-params = ["db"]               # untyped code
delegate-to = ["application"]               # layer names, prefixes or selectors
decorators = ["shop.http.endpoint"]         # in-house endpoint decorators
frameworks = ["fastapi", "django"]          # default: whatever the file mentions
base-classes = ["shop.http.Resource"]       # in-house view base classes
```

- `max-statements`, `max-branches`, `max-nesting`: liczba całkowita od 0 do 1000 albo `false`, żeby wyłączyć sprawdzenie.
- `deny-calls`, `extend-deny-calls`, `deny-receiver-types`, `decorators`, `base-classes`: kwalifikowane nazwy z `*` i `?` jako wildcardami. `deny-calls = []` wyłącza sprawdzanie wywołań; `deny-receiver-types` zastępuje swoją domyślną listę (`sqlalchemy.orm.Session`, `sqlalchemy.orm.session.Session`, `sqlalchemy.ext.asyncio.AsyncSession`, `sqlalchemy.ext.asyncio.session.AsyncSession`, `sqlmodel.Session`, `sqlmodel.ext.asyncio.session.AsyncSession`).
- `delegate-to`: nazwa warstwy z `layers` albo prefiks lub selektor modułu w gramatyce `layers[].modules`. Wpis, który nie jest żadnym z nich, to błąd konfiguracji.
- `frameworks`: różne wpisy spośród `fastapi` (razem ze Starlette), `flask`, `litestar` i `django` (razem z DRF). Bez ustawienia rozpoznawanie frameworka działa w każdym pliku, który o nim wspomina.
- ORM Django: wywołanie managera, takie jak `Order.objects.filter(...)`, domyślnie nie jest zakazane, bo tak kod Django czyta bazę danych, a domyślny zakaz oznaczałby każdy widok. Żeby traktować je w widoku jako pracę na bazie danych, dodaj `extend-deny-calls = ["*.objects.*"]`. Surowe `connection.cursor()` z Django jest na domyślnej liście.

Każde zgłoszenie można wyciszyć w linii przez `# inwards: ignore[INW012] reason="..."` na linii, na której jest zgłoszone: linii `def` albo, dla handlera z innego modułu, linii rejestracji.

[Szablon](../guides/configuration.md#template-rules) może włączyć INW012 dla jednej ze swoich ról, razem z opcjami: `router = { thin-endpoint = { max-statements = 8 } }` ustawia `modules` na moduły roli.

## Znane ograniczenia { #known-limitations }

- **Logika biznesowa czy prezentacja.** Endpoint, który buduje CSV, stronicuje albo ustawia nagłówki cache, jest długi z dobrych powodów. Zgłoszenie podaje liczby, nie werdykt; podnieś próg albo zawęź `modules`.
- **Proste aplikacje CRUD.** Niektóre zespoły celowo wybierają `db.get(...)` w handlerze. Dlatego reguła jest opt-in.
- **Pośredniość.** `s = db; s.execute(...)`, sesja przekazana przez `**kwargs`, alias typu importowany z innego modułu i adnotacje w napisach ukrywają wywołania. Funkcje pomocnicze są śledzone tylko we własnym module endpointu i tylko do trzech wywołań w głąb; funkcja pomocnicza importowana z innego modułu, metoda klasy i funkcja przechowywana w zmiennej albo słowniku nie są śledzone.
- **Handlery rejestrowane z innego modułu** są zgłaszane tam, gdzie się je rejestruje, a nie tam, gdzie są zdefiniowane. Sprawdzenie po edycji modułu handlera (hook PostToolUse po edycji w nim) nie widzi rejestracji; widzi ją pełne sprawdzenie (`inwards check`, Stop gate) i edycja pliku, który rejestruje.
- **Framework jest wykrywany po tekście.** Plik jest czytany pod kątem frameworka tylko wtedy, gdy o nim wspomina, więc blueprint importowany z modułu projektu (`from shop.web import bp`) w pliku, który nigdzie nie mówi `flask`, nie jest rozpoznawany, a klasa bazowa widoku z innego modułu jest śledzona tylko w pliku, który wspomina Django, DRF albo Flaska. Takie klasy bazowe wpisz do `base-classes`.
- **Nie są łączone:** `include(...)` w `urls.py`, `as_view()` w rejestracji (zamiast tego liczą się własne metody klasy), `Mount` i `add_route` Starlette, `register_blueprint` Flaska, `Router(route_handlers=[...])` Litestara dla funkcji bez dekoratora oraz handler przekazany przez zmienną.
- **Odziedziczone handlery.** Widok generyczny, który nadpisuje tylko hooki (`get_queryset`, `perform_create`, `get_serializer_class`), nie jest sprawdzany: hooki nie są handlerami żądań, a handlery są we frameworku.
- **Warunki ochronne.** Jako mapowanie błędu na HTTP liczą się `HTTPException` (z dowolnego frameworka, po nazwie), wyjątki Werkzeuga, Litestara i DRF, `Http404` i `PermissionDenied` z Django oraz `abort(...)` z Flaska. Podklasa z kodu projektu rzucona w warunku ochronnym liczy się jako instrukcja i gałąź.
- **Własne dekoratory**, które opakowują handler i same wykonują pracę, nie są czytane.
- **Fałszywe alarmy:** metoda `execute` na serwisie omyłkowo otypowanym jako `Session`. Wyrażenie listowe z I/O liczy się jako dozwolone, choć wywołania w nim są nadal sprawdzane.
- **Progi** to pierwsze przybliżenie, jeszcze niedostrojone na korpusie; zbyt ciasne progi skłaniają agentów do dzielenia handlerów na bezsensowne funkcje pomocnicze.
