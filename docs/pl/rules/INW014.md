# INW014 `ports-abstract`

## Co robi { #what-it-does }

Opt-in, a po włączeniu błąd. Sprawdza klasy najwyższego poziomu w module portu, czyli module, który deklaruje, co implementują adaptery (`shop/application/ports/orders.py`). Zgłasza trzy rzeczy:

- **Klasę konkretną**, na jej nazwie: klasę, która nie jest ani ABC, ani Protocol i nie rozszerza klasy z modułu portu. Klasa jest ABC, gdy wśród jej baz jest `abc.ABC` albo jej metaklasą jest `abc.ABCMeta`, a Protocol, gdy wśród baz jest `typing.Protocol` (albo `typing_extensions.Protocol`), także w postaci `Protocol[T]` i `class P[T](Protocol)`.
- **Metodę, która wykonuje pracę**, na nazwie metody: metodę ABC albo Protocol, której ciało zawiera coś innego niż docstring, `...`, `pass` albo `raise NotImplementedError` (z komunikatem albo bez). Liczą się też metody z dekoratorami, w tym `@property` i `@abstractmethod`.
- **Implementację**, na nazwie klasy: klasę, która rozszerza port z modułu portu, sama nie wymienia `ABC` ani `Protocol` i ma metody wykonujące pracę. Zgłoszenie jest jedno i wymienia wszystkie takie metody.

Podklasa portu, której wszystkie metody są abstrakcyjne, jest węższym portem i przechodzi. Przechodzą też wyjątki, modele Pydantic, named tuple, typed dict, enumy i dataclassy: zobacz [Konfiguracja](#configuration).

Bez `modules` reguła sprawdza każdy moduł, który ma w nazwie segment `ports`: `shop.application.ports`, `shop.application.ports.orders`, `shop.billing.ports.payments`. Ustaw `modules`, żeby sprawdzać inne moduły.

## Dlaczego to źle { #why-is-this-bad }

W architekturze czystej i heksagonalnej warstwa aplikacji deklaruje porty, klasy abstrakcyjne albo Protocol, a adaptery z zewnętrznej warstwy je implementują. Agenci często dopisują w module portu implementację „domyślną”: metodę, która zapisuje do bazy, `print`, repozytorium w pamięci obok interfejsu. Warstwa aplikacji zawiera wtedy I/O albo logikę adaptera, reguła zależności obowiązuje tylko na papierze, a następny agent rozbudowuje implementację domyślną zamiast napisać adapter.

Python pozwala na oba skróty. Metoda z `@abstractmethod` może mieć ciało, które podklasy wywołują przez `super()` ([dokumentacja `abc`](https://docs.python.org/3/library/abc.html#abc.abstractmethod)), a metody Protocol mogą mieć domyślne ciała, które dziedziczą jawne podklasy ([specyfikacja typowania, Protocols](https://typing.python.org/en/latest/spec/protocol.html)). [B024](https://docs.astral.sh/ruff/rules/abstract-base-class-without-abstract-method/) i [B027](https://docs.astral.sh/ruff/rules/empty-method-without-abstract-decorator/) w Ruff sprawdzają tylko klasy ABC, w każdym module, i nic nie mówią o klasie konkretnej ani o ciele metody w porcie. INW014 sprawdza moduły portów i nic więcej.

```python title="shop/application/ports/orders.py"
from abc import ABC, abstractmethod
from typing import Protocol


class OrderNotFound(Exception):
    pass


class Clock(Protocol):
    def now(self) -> float: ...


class OrderRepository(ABC):
    @abstractmethod
    def get(self, order_id: int) -> dict:
        """Loads one order, or raises OrderNotFound."""

    def save(self, order: dict) -> None:
        print("saving order", order["id"])


class InMemoryOrders(OrderRepository):
    def __init__(self) -> None:
        self.rows: dict[int, dict] = {}

    def get(self, order_id: int) -> dict:
        return self.rows[order_id]


class SmtpMailer:
    def send(self, to: str, body: str) -> None:
        print("mail to", to, body)
```

```python title="shop/infrastructure/orders.py"
from shop.application.ports.orders import OrderNotFound, OrderRepository


class InMemoryOrders(OrderRepository):
    def __init__(self) -> None:
        self.rows: dict[int, dict] = {}

    def get(self, order_id: int) -> dict:
        if order_id not in self.rows:
            raise OrderNotFound(order_id)
        return self.rows[order_id]

    def save(self, order: dict) -> None:
        self.rows[order["id"]] = order
```

## Jak działa { #how-it-works }

Plik jest parsowany tylko wtedy, gdy INW014 jest włączona dla jego modułu, moduł jest modułem portu, a tekst zawiera słowo `class`. Jedno parsowanie na taki plik; żaden inny moduł nie jest czytany.

- **Nazwy** są kwalifikowane przez importy pliku, więc liczą się `import abc` z `abc.ABC`, `from typing_extensions import Protocol` i import z aliasem. Nazwa, której plik nie importuje i nie definiuje jako klasy, jest wbudowana i zapisana bez prefiksu (`Exception`, `ValueError`).
- **Bazy z modułu portu.** Baza zdefiniowana w tym samym pliku albo zaimportowana z innego modułu portu (z segmentem `ports` albo pasującego do `modules`) czyni klasę węższym portem albo implementacją. Jej własny moduł jest sprawdzany osobno.
- **Kolejność.** Dozwolony dekorator albo baza zwalnia klasę bez względu na jej pozostałe bazy. W przeciwnym razie `Protocol` albo `ABC` wśród jej własnych baz czyni ją interfejsem, także gdy rozszerza ona inny port.
- **Ciała.** Docstring, każdy inny napis, `...`, `pass` oraz `raise NotImplementedError` albo `raise NotImplementedError("...")` są abstrakcyjne; komentarze się nie liczą. Komunikat cytuje pierwszą inną instrukcję.
- **Ciała klas.** Sprawdzane są tylko metody. Atrybuty, adnotacje i stałe w ciele klasy przechodzą, podobnie jak klasy zagnieżdżone.
- **Poprawka** wskazuje warstwę adapterów: pierwszą warstwę, której nazwa mówi outbound, driven albo secondary, w drugiej kolejności infrastructure albo persistence, w trzeciej adapter, i jej pierwszy wpis w `modules`. Bez takiej warstwy mówi o module adaptera poza pakietem portów.

## Jak naprawić { #how-to-fix }

1. Zostaw interfejs w module portu: ABC z metodami `@abstractmethod` albo Protocol, każde ciało to `...` albo docstring.
2. Przenieś kod do klasy w warstwie adapterów, która dziedziczy po ABC albo ma metody Protocol.
3. Przenieś dubel testowy (fake w pamięci) obok testów albo do modułu adaptera.
4. Jeśli klasa to dane, a nie interfejs (wyjątek, DTO, obiekt wartości), daj jej bazę albo dekorator, który to mówi, albo poproś właściciela konfiguracji o dodanie jej bazy do `extend-allow-bases`.

## Bezpieczeństwo poprawki { #fix-safety }

Brak automatycznej poprawki (`autofix: false`). Przeniesienie klasy zmienia jej ścieżkę importu u każdego wywołującego, a adapter, który polegał na domyślnym ciele metody, musi ją zaimplementować.

## Konfiguracja { #configuration }

Ważność: błąd. Opt-in: włącz ją przez `extend-select`. Opcje są w `[tool.inwards.rules.ports-abstract]` ([tabele opcji](index.md#opt-in-rules)):

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards.rules]
extend-select = ["INW014"]

[tool.inwards.rules.ports-abstract]
modules = ["shop.application.ports", "shop.*.ports"]  # optional: the port modules
extend-allow-bases = ["shop.domain.ValueObject"]      # more bases that are exempt
allow-decorators = ["dataclasses.dataclass", "attrs.*"]
```

- `modules`: prefiksy modułów albo selektory, jak w `modules` warstwy. Gdy jest ustawione, INW014 sprawdza pasujące moduły zamiast tych z segmentem `ports`, a baza zaimportowana z jednego z nich liczy się jako port.
- `allow-bases`: kwalifikowane nazwy, z `*` i `?` jako wildcardami, baz, które zwalniają klasę. Nazwy wbudowane pisze się bez prefiksu. Ustawienie zastępuje domyślną listę: `BaseException`, `Exception`, `*Error`, `*Exception`, `*Warning`, `pydantic.BaseModel`, `typing.NamedTuple`, `typing.TypedDict`, ich odpowiedniki z `typing_extensions` i `enum.*`.
- `extend-allow-bases`: bazy dodane do `allow-bases` albo do jej domyślnej listy.
- `allow-decorators`: kwalifikowane nazwy, z wildcardami, dekoratorów klas, które zwalniają klasę. Ustawienie zastępuje domyślną listę: `dataclasses.dataclass`, `pydantic.dataclasses.dataclass`, `attrs.define`, `attrs.frozen`, `attrs.mutable`, `attr.s`, `attr.attrs`, `attr.define` i `attr.frozen`.

Żeby zaakceptować jedno zgłoszenie, wycisz je w linii, na którą wskazuje: `# inwards: ignore[INW014] reason="..."` w linii `class` albo `def`.

## Znane ograniczenia { #known-limitations }

- **Tylko klasy najwyższego poziomu.** Klasa wewnątrz funkcji albo pod `if TYPE_CHECKING:`, klasa zagnieżdżona i funkcje na poziomie modułu nie są sprawdzane. Moduł portu z konkretną funkcją przechodzi.
- **Bazy po nazwie.** Klasa, która dostaje `ABCMeta` przez bazę spoza modułów portów (`class Repo(SomeLibraryBase)`), jest zgłaszana jako konkretna; dodaj bazę do `extend-allow-bases` albo wymień też `ABC`. Baza z modułu portu liczy się bez czytania, więc konkretna klasa w tamtym module jest zgłaszana w swoim module, nie przez podklasy.
- **Klasy zwolnione nie są sprawdzane dalej.** Wyjątek albo dataclass w module portu może mieć dowolne metody; `allow-bases` decyduje tylko o tym, czy klasa to dane.
- **Ciała klas.** Atrybut klasy, który buduje obiekt (`session = Session()`), nie jest zgłaszany.
- **Domyślne ciała, na które pozwala język.** Metoda `@abstractmethod` z ciałem dla `super()` albo metoda Protocol z domyślnym ciałem jest zgłaszana: przenieś wspólny kod do funkcji pomocniczej poza portem albo wycisz linię z podaniem powodu.
