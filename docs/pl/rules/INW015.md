# INW015 `construct-only-in`

## Co robi { #what-it-does }

Opt-in, a po włączeniu błąd. Wskazujesz rolę, czyli moduły, które może budować tylko korzeń kompozycji, na przykład adaptery wyjściowe, oraz moduły, którym wolno je budować. INW015 zgłasza wtedy dwie rzeczy w każdym innym module, który należy do warstwy:

- **Import modułu roli, który się wykonuje.** Liczy się zwykły import, import `from`, import względny, import z gwiazdką i import wewnątrz funkcji; zgłoszenie stoi na importowanej nazwie. Import w bloku `if TYPE_CHECKING:` (albo `if typing.TYPE_CHECKING:`) się nie liczy: nigdy się nie wykonuje, więc niczego nie buduje.
- **Wywołanie, które buduje klasę roli osiągniętą inną drogą.** `SqlOrderRepo()` po `from store.adapters import SqlOrderRepo`, gdy `store/adapters/__init__.py` ją reeksportuje, albo `store.adapters.outbound.sql.SqlOrderRepo()` po `import store.adapters`. Zgłoszenie stoi na wywołaniu. Wywołanie, którego nazwa pochodzi z importu już zgłoszonego przez INW015, nie jest zgłaszane drugi raz.

Moduły roli mogą importować siebie nawzajem, podobnie jak moduły wymienione w `allowed-in`. Moduł, który nie należy do żadnej warstwy, na przykład test albo skrypt, nie jest sprawdzany: testy budują adaptery celowo.

## Dlaczego to źle { #why-is-this-bad }

W architekturze portów i adapterów warstwy wewnętrzne mają port (klasę abstrakcyjną albo `Protocol`), adapter wyjściowy go implementuje, a korzeń kompozycji (`main.py`, `di.py`) buduje adapter i przekazuje go temu, kto potrzebuje portu. Gdy adapter wejściowy, na przykład kontroler REST, sam buduje `SqlOrderRepo()`, tego połączenia już nie ma: kontroler jest związany z SQL, test nie podstawi atrapy, a kolejny agent skopiuje ten wzorzec do każdej trasy.

INW001 tego nie widzi. Adaptery wejściowe i wyjściowe zwykle leżą w tej samej warstwie, więc import nie jest skierowany na zewnątrz. Moduły publiczne z INW003 dotyczą kontekstów ograniczonych, a nie tego, kto może co budować.

## Przykład { #example }

```toml title="pyproject.toml"
  { name = "application", modules = ["store.application"] },
  { name = "adapters", modules = ["store.adapters"] },
  { name = "bootstrap", modules = ["store.main"] },

[tool.inwards.rules]
extend-select = ["INW015"]

[tool.inwards.rules.construct-only-in]
```

```text
store/adapters/inbound/rest.py:1:41: INW015 `store.adapters.inbound.rest` imports `SqlOrderRepo` from `store.adapters.outbound.sql`, a module of the role `store.adapters.outbound`, which only `store.main` may import. A module that uses the adapter directly is tied to it and bypasses the port it implements.
  fix: Take the port as a parameter instead of importing `store.adapters.outbound.sql`, and let `store.main` build the adapter.
    1. Delete `from store.adapters.outbound.sql import SqlOrderRepo`.
    2. Type this module against the port the adapter implements (the abstract class or Protocol the inner layer owns), not against the adapter.
    3. Receive the implementation through a constructor or function parameter; in a FastAPI route or dependency, through `Depends()` on a provider whose return type is the port.
    4. Build the adapter in `store.main` and pass it in from there.
```

Import w `TYPE_CHECKING` też przechodzi, bo nigdy się nie wykonuje. Nadal jednak wiąże moduł z nazwą adaptera, więc w adnotacjach lepiej używać portu:

```python title="store/adapters/inbound/rest.py"
from typing import TYPE_CHECKING

if TYPE_CHECKING:

```

## Jak działa { #how-it-works }

INW015 sprawdza moduł, gdy reguła jest dla niego włączona (`modules`), moduł należy do warstwy i nie jest ani w `role`, ani w `allowed-in`. Plik bez słowa `import` nigdy nie jest parsowany; każdy inny jest parsowany raz, osobno.

- **Importy.** Każda instrukcja importu, także zagnieżdżona, jest rozwiązywana tak jak w INW001, a indeks modułów projektu mówi, w którym module z własnego kodu ląduje. Zgłaszany jest import, który ląduje w module roli i nie leży w ciele gałęzi `if TYPE_CHECKING:` albo `elif TYPE_CHECKING:`. Gałąź `else` się wykonuje, więc się liczy.
- **Wywołania.** Wywołanie, w którym ostatnia nazwa wywoływanego obiektu zaczyna się wielką literą, tak jak Python nazywa klasy, jest kwalifikowane przez importy pliku i śledzone przez indeks modułów, przez najwyżej cztery reeksporty, aż do `class` z najwyższego poziomu. Jeśli ta klasa jest zdefiniowana w module roli, wywołanie jest zgłaszane. Czytane są tylko moduły z roli, z `allowed-in` i pakiety nad rolą (których `__init__.py` może ją reeksportować), każdy raz na sprawdzany plik.
- **Najpierw INW001.** Import skierowany na zewnątrz, do innej warstwy, dostaje tylko INW001, którego poprawka już każe zależeć od portu. Gdy INW001 jest wyłączona dla modułu, zgłasza go INW015.

## Jak naprawić { #how-to-fix }

1. Zależ od portu, który adapter implementuje, a nie od adaptera.
2. Przyjmij implementację jako parametr konstruktora albo funkcji. W trasie albo zależności FastAPI użyj `Depends()` z funkcją dostarczającą, której typ zwracany to port.
3. Zbuduj adapter w korzeniu kompozycji i przekaż go stamtąd.

## Bezpieczeństwo poprawki { #fix-safety }

Brak automatycznej poprawki (`autofix: false`). Przeniesienie budowania do korzenia kompozycji zmienia konstruktory i miejsca wywołań w więcej niż jednym module.

## Konfiguracja { #configuration }

Ważność: błąd. Opt-in: włączasz ją przez `extend-select`. Presety `clean` i `hexagonal` polecenia [`inwards init`](../guides/install.md#a-new-project-start-from-a-preset) włączają INW015 jako ostrzeżenie, z adapterami wyjściowymi (`app.infrastructure` albo `app.adapters.outbound`) jako `role` i `app.bootstrap` jako `allowed-in`. Opcje trafiają do `[tool.inwards.rules.construct-only-in]` ([tabele opcji](index.md#opt-in-rules)):

<!-- config: fragment -->

```toml title="pyproject.toml"
[tool.inwards.rules]
extend-select = ["INW015"]

[tool.inwards.rules.construct-only-in]
role = ["app.adapters.outbound", "app.*.gateways"] # required: the guarded modules
allowed-in = ["app.di", "app.main"]                # the composition root
modules = ["app.adapters"]                         # optional: only report here
```

- `role` (wymagane): prefiksy modułów albo selektory, zapisane jak w `modules` warstwy, wskazujące moduły, które może importować i budować tylko korzeń kompozycji. Prefiks obejmuje pakiet i wszystko pod nim. Tabela bez `role` to błąd konfiguracji.
- `allowed-in`: prefiksy modułów albo selektory korzenia kompozycji, który może importować rolę i budować jej klasy. Bez tej opcji mogą to robić tylko moduły samej roli.
- `modules`: jak w każdej regule, moduły, w których INW015 zgłasza. Inaczej niż w większości reguł nie wskazuje roli: od tego jest `role`.

Pojedynczy import można wyciszyć z uzasadnieniem w jego linii: `# inwards: ignore[INW015] reason="..."`.

[Szablon](../guides/configuration.md#template-rules) może włączyć INW015 dla jednej ze swoich ról: `outbound = { construct-only-in = { allowed-in = ["app.di"] } }` wpisuje moduły roli do `role`, a nie do `modules`, więc to rola jest tym, co reguła chroni.

## Znane ograniczenia { #known-limitations }

- **Tylko klasy, po nazwie.** Forma wywołań śledzi wywoływany obiekt, którego nazwa zaczyna się wielką literą, więc funkcja fabrykująca (`make_repo()`) albo klasa z nazwą małą literą osiągnięta przez reeksport nie jest śledzona. Jej import, gdy importuje moduł roli wprost, nadal jest zgłaszany.
- **Co ukrywa klasę.** Klasa przypisana pod inną nazwę (`Repo = SqlOrderRepo`), przekazywana jako wartość albo podana do `Depends(SqlOrderRepo)` przez reeksport nie jest śledzona. Jej bezpośredni import i tak jest zgłaszany.
- **Reeksporty.** Śledzone są najwyżej cztery reeksporty, i tylko przez rolę, `allowed-in` i pakiety nad rolą.
- **Moduły spoza warstw** nie są sprawdzane wcale, więc kod poza twoimi warstwami może budować adaptery bez ograniczeń.
- **Jedno zgłoszenie na import, a nie na użycie.** Poprawienie importu poprawia każde jego użycie.
