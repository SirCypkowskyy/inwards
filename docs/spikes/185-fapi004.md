# Spike #185: can Inwards prove endpoint exceptions are handled? (FAPI004)

**Outcome: no-go for FAPI004 as a rule.** None of subsets A to E is worth a rule
code of its own. Subset B's lessons go to FAPI002's ring 3 (#183), and D is
already FAPI007 (#226). The reserved code `unhandled-exception` should be
released.

| Subset | Verdict | Key numbers (25 repos, 4,698 endpoints) |
|---|---|---|
| A. Declared classes without a handler | **No-go** | 217 findings in 8 repos, 177 once unresolved registrations make a repo go quiet. Hand-classified precision 1 of 33 (3%), 0 of 9 in `*exceptions*`/`*errors*` modules. Quiet in 12 repos only because they have a catch-all; the strict variant (catch-all doesn't count) gives 1,235 findings in 20 repos. |
| B. Raised in rings 0-2, no handler | **No-go as FAPI004**; lessons go to FAPI002 ring 3 | 3,142 raises in reach, 518 caught by a caller's try. 65 unhandled raise sites in 3 repos (6 classes each in onyx and fief, 1 in khoj). Precision 4 of 30 (13%) on the sample; 4 true findings in the whole corpus. |
| C. Middleware catch | **Decidable and precise, but only a helper** | 25 try blocks around `call_next`/`self.app`. The naive test (no bare `raise`) picks 14, of which 7 are wrong; the refined test (no `raise` at all, no second call into the app) picks 7, all 7 right. |
| D. Yield dependency swallows | **No-go under FAPI004** (it is FAPI007, #226) | 29 yield dependencies, 2 with an `except` around the `yield`, 0 that swallow. |
| E. Full coverage | **No-go** | Not decidable (see the issue). The corpus adds nothing new. |

## Method

- **Corpus:** 25 open-source FastAPI apps, cloned with `git clone --depth 1`
  (list and commits below): the FastAPI projects of the bench corpus (#36:
  full-stack-fastapi-template, fastapi-clean-example, python-ddd, polar), the
  apps named in the issue (Netflix Dispatch, mealie, fief) and 18 others,
  from 18-file templates to litellm's 2,817 files. 13,269 first-party `.py`
  files in all (tests, migrations, docs and virtualenvs excluded), 65 `FastAPI(...)`
  constructions, 4,698 path operations, 86 handler registrations.
- **Script:** [`185-fapi004.py`](185-fapi004.py), plain Python `ast`. It never
  imports or runs a project. Run it with
  `uv run --no-project python docs/spikes/185-fapi004.py CORPUS_DIR --json out.json`.
  Its stdout for this run is [`185-fapi004-results.tsv`](185-fapi004-results.tsv).
  It resolves names through imports by dotted-path suffix, follows `from x import *`,
  unrolls `for exc in [A, B]: app.add_exception_handler(exc, h)`, and reads
  `exception_handlers=` as a keyword or as a `{"exception_handlers": {...}}`
  dict splatted into `FastAPI(**kwargs)`.
- **Handlers:** `@x.exception_handler(E)`, `x.add_exception_handler(E, h)` and
  `exception_handlers={E: h}`, matched by MRO over first-party classes, the way
  Starlette's `_lookup_exception_handler` does it. `HTTPException`,
  `WebSocketException` and `RequestValidationError` subclasses count as
  handled by FastAPI's defaults. A registration whose class can't be resolved
  counts as `unres`. A rule would go quiet for that app, and the `A_silent_unh`
  column does the same.
- **Rings (B):** the endpoint (ring 0), then first-party functions called by
  name and `Depends`/`Security` targets (including `Annotated` aliases defined
  at module level), up to depth 2. The same bounds as FAPI002 in #183. Method
  calls on objects (ring 4) are not followed.
- **Hand classification:** a finding is a true positive when the exception
  can reach the app from that endpoint and, as far as the code shows, the
  client gets a 500 that nobody intended. The sampled items are below.

Two things the script does that a rule should not, both deliberate for the
spike and both called out where they matter: it takes the **union of handlers
across all apps** in a repo, and it can't see **MRO through third-party
classes**.

## What the corpus says before any subset

- **12 of 25 repos have a catch-all.** 9 register an `Exception` handler
  (argilla, fastapi-clean-example, fastapi_best_architecture, langflow,
  litellm, llama-stack, lnbits, polar, prefect) and 3 have middleware that
  catches `Exception` and returns a response (FastAPI-boilerplate, dispatch,
  gpustack). With the catch-all counting as handled, as the issue proposed, A
  and B say nothing there by construction.
- **5 repos register no handler at all** (chainlit, fastapi-react,
  full-stack-fastapi-template, khoj, minimal-fastapi-postgres-template). They
  translate at the route: `except DomainError: raise HTTPException(...)`.
- **Registrations are often dynamic.** fief fills a module-level dict with
  `exception_handlers[X] = h` and registers it in a loop, and argilla loops
  over a list (unrolled here). prefect passes a dict literal into
  `FastAPI(**kwargs)`. The #186 model reads only the keyword, so it would miss
  prefect's `Exception` handler and report all 149 of its classes.
- **Handlers are per app, and repos have several apps** (65 apps in 25 repos).
  polar's only `Exception` handler is on its worker health-check app
  (`polar/worker/_health.py`), not on the API. The script's union across
  apps hides that. A rule has to scope handlers per app through #184's
  include graph, and then polar's API gets findings. Those are mostly false
  positives: see "External bases" below.

## A. Declared exception classes without a handler: no-go

| | Count |
|---|---:|
| First-party exception classes (not `HTTPException` subclasses) | 1,711 in 22 repos |
| With no handler by MRO (catch-all counts) | 217 in 8 repos |
| ... and the repo has no unresolved registration | 177 in 7 repos |
| ... declared in an `*exception*`/`*error*` module | 50 in 5 repos |
| ... and raised somewhere, and not a base class | 35 in 5 repos |
| Strict: no handler, catch-all doesn't count | 1,235 in 20 repos |
| Handled only thanks to middleware (C) | 49 in 3 repos |

Hand classification: 33 of the 177, sampled across the 7 repos (seed 185).

| Result | n | Why |
|---|---:|---|
| True positive | 1 | khoj `RetryableModelError`: raised when every model fails, reaches `POST /title` uncaught. |
| Unclear | 1 | chainlit `ChainlitContextException`: a "no context" guard, reachable only through misuse. |
| FP: caught and translated before the app | 14 | onyx `SizeCapExceeded`, `DriveItemContentError`, `ToolExecutionException`, `_NoCandidateFound`, `BoxGroupTooLargeError`, `UsageLimitExceededError`, `KvKeyNotFoundError`; mealie `RateLimitError`, `InvalidDomainError`, `NoEntryFound`, `AIProviderNotEnabledError` (`except Exception` plus `isinstance`); python-ddd `InvalidCredentialsException`; open-webui `YoutubeTranscriptError`; realworld `EntityDoesNotExist`. |
| FP: never raised, or only a base class | 7 | onyx `ActivityTimeoutError`; mealie `ForcedTimeoutException`; python-ddd `ApplicationException`, `InfrastructureException`, `InvalidAccessTokenException`, `UnitOfWorkNotSetException`. |
| FP: not on an HTTP path (workers, connectors, tools, build scripts, validators) | 10 | onyx `InsufficientPermissionsError`, `CodeInterpreterVersionError`; mealie `DurationError`, `UnitNotSupported` (dev script), `UnitNotFound`; chainlit `BuildError`, `McpDestinationError`; khoj `GeminiRetryableClientError`, `TextToSpeechError`; open-webui `MatchBudgetExceeded`, `ChatVariablesError`. |

**Precision 1/33 (3%).** Restricting to exception modules doesn't help: the 9
sampled items in `*exceptions*`/`*errors*` modules are all false positives.
Most projects that have no catch-all translate exceptions at the route, and
many exception classes belong to background workers, connectors or the CLI
that share the package. "Declared, no handler" is the normal state of a
healthy FastAPI codebase, not a smell. The recommendation's premise (agents add
a class to `exceptions.py` and the client gets a 500) doesn't show up in 25
repos. A class only matters when it is raised where an endpoint can reach it,
and that is B.

A config such as `exception-modules` plus `base-classes` would reduce the
noise only by having the user list exactly the classes that must have a
handler. That is a hand-kept list the rule can't check any better than a test.

## B. Raised in rings 0-2 without a handler: no-go as FAPI004

| | Count |
|---|---:|
| First-party custom exceptions raised in reach (rings 0-2) | 3,142 in 15 repos |
| Caught by a try/except in a caller on the path (subtracted) | 518 |
| Unhandled by MRO (catch-all counts) | 65 raise sites in 3 repos (onyx 18, fief 46, khoj 1) |
| ... in repos with no unresolved registration | 19 (onyx, khoj) |
| Strict: catch-all doesn't count | 230 in 9 repos |

Before the caller-catch subtraction the count was 135 unhandled sites
(onyx 77, open-webui 6, khoj 5, fief 47). The usual pattern,
`try: helper() except X: raise HTTPException(...)`, is invisible when you only
look at a `try` around the `raise` itself. FAPI002 plans to subtract these
(#183, "False positives"), and this shows the subtraction is required, not
optional.

Hand classification: 30 unhandled sites (all 16 unique sites in onyx and khoj,
plus 14 from fief).

| Result | n | Items |
|---|---:|---|
| True positive | 4 | onyx `ConnectorValidationError` from `validate_ccpair_for_user` in `PUT /admin/credential/swap`; onyx `EERequiredError` in `POST /admin/slack-app/channel` (a user input gives a 500 instead of a 4xx); onyx `CacheLockAcquisitionError` in `PATCH /admin/settings` (lock timeout, a 503 would be honest); khoj `RetryableModelError` in `POST /title`. |
| Unclear | 1 | onyx `MCPCredentialsError`: a branch for anonymous users on a PT_OAUTH server that this endpoint's permission may exclude. |
| FP: dynamic registration | 14 | fief `AuthorizeException`, `AuthorizeRedirectException`, `LoginException`, `OAuthException`, `TokenRequestException`, `LogoutException`, all registered through `exception_handlers[X] = h` plus a loop. |
| FP: raised inside a generator passed to `StreamingResponse` | 11 | onyx `SnapshotError` in the sandbox sidecar's `iter_snapshot_archive`. The response has already started, so no handler can turn it into a status code. The sidecar is also a separate app. |

**Precision 4/30 (13%).** If the rule stays quiet on unresolved registrations
and skips generators handed to `StreamingResponse`, the corpus has 5 distinct
findings, 4 of them true, across 4,698 endpoints. The catch-all repos were
checked in strict mode (10 of the 230 sites, one per class): 2 true (langflow
`PolicyBundleNotInitializedError` and `EndUserIdentityRequiredError`, caught
on sibling endpoints but not on these), 7 false and 1 unclear. The false ones:
polar `InsufficientScopeError`/`InvalidTokenError` derive from authlib's
`OAuth2Error`, which has a handler; llama-stack's `Exception` handler switches
on type; fastapi-clean-example's `ProbeError` and debug `InternalServerError`
are meant to be 500s; gpustack's `PDModeCatalogError` is a broken bundle, where
500 is right; polar `UnsafeCrawlableUrl` is converted by its caller.

Four true findings in 25 repos don't justify a rule code. They also come from
the ring walk FAPI002 already does: its ring 3 looks up raised custom
exceptions by MRO against app handlers. What B needs is already in FAPI002's
plan, plus the guards listed under "Lessons for FAPI002".

## C. Middleware catch: decidable, precise, a helper only

| | Count |
|---|---:|
| try blocks around `call_next` (function or `BaseHTTPMiddleware.dispatch`) | 17 in 9 repos |
| try blocks around `self.app(scope, receive, send)` (pure ASGI) | 8 in 5 repos |
| Naive "handles" (no bare `raise` in the except) | 14 |
| Refined "handles" (no `raise` at all, no second call into the app) | 7 in 4 repos |

All 25 were classified by hand. The refined test is right on 7 of 7:
FastAPI-boilerplate's `CatchAllErrorMiddleware`, dispatch's
`ExceptionMiddleware` (3 clauses), gpustack's `RequestTimeMiddleware` and its
proxy's `NotFoundException` clause, and khoj's `ClientDisconnect` clause. The
naive test gets 7 of 14 wrong: `raise e` / `raise e from None` (dispatch ×2,
teamhide/fastapi-boilerplate), a retry through `call_next` in argilla's
monitoring middleware, llama-stack's zstd fallback that replays the request,
gpustack's proxy that falls through to `call_next` on `HTTPException`, and
khoj's `HTTPException` clause, which redirects 5xx on web routes and re-raises
the rest. The refined test leaves that last one out, which is the safe side. Pure ASGI middleware is
just as readable as `call_next` middleware here. The issue expected it not to
be.

C has no finding of its own. It only tells A and B that a class is handled.
Whether the middleware is actually installed (`add_middleware`,
`Middleware(...)`, `@app.middleware("http")`) and on which app is a graph
question for #184.

## D. Yield dependencies that swallow: no finding

29 generator functions are used as `Depends` targets, 2 have an `except`
around the `yield`, and both re-raise. 102 other generators in FastAPI files
have an `except` without `raise`, but they are streaming bodies and lifespans,
not dependencies. D fired 0 times, so it gives no reason to put it under
FAPI004. It's already planned as FAPI007 `yield-dependency-swallows` (#226).
For #226: it is cheap and precise, but expect it to be rare. The common
`get_db` pattern re-raises.

## E. Full coverage: no-go

Not decidable, for the reasons in the issue. The corpus adds concrete cases:
exceptions raised in streaming bodies (no handler can apply), handlers that
switch on type inside an `Exception` handler (llama-stack, argilla), MRO
through third-party bases (authlib), and handlers per app.

## Cost

A full run parses the files the #186 model already reads (1,683 in the corpus)
plus:

- A: files that declare exception classes and don't import FastAPI: **+573
  files (+34%)**.
- B: files the rings reach that don't import FastAPI: **+851 files (+51%)**.

A hook call on one file would read lazily through `ProjectIndex`: the app
module's registrations, the classes on the MRO and the functions in the rings
of the edited endpoint. That is a handful of files. Cost doesn't decide the
verdict, precision does.

## Lessons for FAPI002 ring 3 (#183)

FAPI002 already walks rings 0-2 and looks up raised custom exceptions against
app handlers by MRO. The corpus says that walk needs these guards to stay quiet:

1. Subtract a `try`/`except` around the call on the path, not only around the
   `raise` (518 raises in the corpus are caught by a caller).
2. Go quiet for an app when a registration can't be resolved (fief's dict
   plus loop). Unroll a loop over a list literal (argilla). Read
   `exception_handlers` from a dict literal splatted into `FastAPI(**kwargs)`
   (prefect), or treat `**kwargs` as unknown.
3. Scope handlers per app through #184's graph (polar's `Exception` handler is
   on another app).
4. Stop at third-party bases: when the MRO leaves first-party code into a
   non-builtin class, treat the handler lookup as unknown (polar and authlib).
5. Skip raises inside a generator passed to `StreamingResponse` or
   `EventSourceResponse`. Handlers can't map those.
6. Count middleware `except` clauses that neither raise nor call the app
   again as handlers (C's refined test).
